# srrrg UIUX v3 - 구현 결과 및 설계 대비 변경점

이 문서는 `01`~`05` 설계 문서를 실제 코드로 옮기며 생긴 변경점과, 남은 작업을 기록한다. 설계 문서 자체는 수정하지 않고 이 문서에 "실제로는 이렇게 갔다"를 남긴다.

## 1. 구현 범위

| Phase | 상태 | 내용 |
|---|---|---|
| 1. 워크스페이스 셸 | 완료 | 좌측 사이드바 + 상단 바 (`fragments/workspace-shell.html`), `/projects`·`/campaigns`·`/statistics`에 적용 |
| 2. 프로젝트 라우팅 분리 | 완료 (범위 조정) | 멤버(`/projects/members`)·설정(`/projects/settings`) 독립 화면 분리. "개요" 신규 대시보드는 미구현(4장 참고) |
| 3. 링크 화면 통합 | 완료 (범위 조정) | 전역 링크 테이블 대신 링크 상세 드로어(`srrrg-link-drawer.js`)를 프로젝트 링크 목록·캠페인 링크 테이블에 공통 적용 |

| 5. UTM 템플릿 독립 | 완료 | `/projects/utm-templates` 신설 (마스터-디테일 레이아웃) |
| 6. 통계 정리 + 접근성 | 완료 (조사 결과 대부분 기 완료 상태) | 5장 참고 |

## 2. 설계 대비 의도적으로 바꾼 것

### 2.1 라우팅: path-variable 대신 기존 쿼리 파라미터 방식 유지

`02_information_architecture.md`는 `/projects/{id}/members`처럼 path-variable 기반 URL을 제안했다. 하지만 기존 코드베이스(`campaigns.html`, `statistics.html`, `management.html`)가 전부 `?projectId=...` 쿼리 파라미터로 프로젝트를 식별하고, 프론트 JS도 전부 그 전제로 작성되어 있었다. 새 화면만 다른 URL 스킴을 쓰면 사이드바 활성 프로젝트 유지 로직이 두 갈래로 갈라진다.

그래서 실제 구현은 `/projects/members?projectId=...`, `/projects/settings?projectId=...`, `/projects/utm-templates?projectId=...`로 통일했다. IA 문서의 의도(멤버·설정·UTM 템플릿의 독립 화면화)는 그대로 달성했고, URL 스킴만 기존 관례를 따랐다.

### 2.2 캠페인 통계 탭: 재구현 대신 iframe 임베드

`04_screen_specs.md` 6.5절은 캠페인 통계 탭 안에 프로젝트 통계와 동일한 컴포넌트를 다시 그리라고 했다. 이미 `statistics.html` + `srrrg-statistics.js`가 차트·표·필터를 전부 구현하고 있어서, 이 로직을 캠페인 화면에 다시 옮기면 같은 코드가 두 곳에 생긴다.

대신 캠페인 상세의 "통계" 탭은 `<iframe>`으로 기존 `/statistics?projectId=...&campaignId=...`를 그대로 불러온다(탭을 처음 열 때만 로드). 완전한 SPA 느낌은 아니지만, 코드 중복 없이 완전히 동작하는 통계 화면을 얻는다. 더 매끄러운 통합이 필요해지면 그때 `srrrg-statistics.js`를 재사용 가능한 모듈로 뽑는 리팩터링을 고려한다.

### 2.3 전역 링크 테이블 대신 "같은 드로어 재사용"

`04_screen_specs.md` 4장은 프로젝트 전체 링크(캠페인 소속 여부 무관)를 한 테이블에서 검색·필터하는 화면을 제안했다. 이걸 만들려면 "프로젝트의 모든 링크를 커서 페이징으로 조회"하는 **새 백엔드 엔드포인트**가 필요한데, 지금 API는 `standaloneLinks`(캠페인 미소속)와 캠페인별 링크를 따로 조회하는 구조뿐이다.

새 집계 API를 만드는 대신, **링크 상세 드로어**(`srrrg-link-drawer.js`)라는 하나의 컴포넌트를 만들어 프로젝트의 "최근 링크" 목록과 캠페인의 "캠페인 링크" 테이블 양쪽에서 재사용하는 쪽을 택했다. 드로어는 기존 `GET/PATCH/DELETE /api/web/projects/{projectId}/links/{code}`만으로 동작하며 원본 URL·만료 수정, 삭제, 전체 관리 화면(`/manage`)으로의 이동을 제공한다. "프로젝트 전체를 가로지르는 검색"은 여전히 없다 — 이건 새 백엔드 작업이 필요한 항목으로 아래 4장에 남겨둔다.

### 2.4 캠페인 삭제 → "보관" 용어 정정

캠페인 삭제는 이미 `@SoftDelete`(is_deleted 플래그)로 구현되어 있어 링크가 함께 사라지지 않는데, 기존 확인 문구는 "소속된 모든 링크가 함께 삭제됩니다"라고 안내하고 있었다(soft delete 전환 이전 문구가 남아있던 것으로 보임). 버튼을 `보관하기`로 바꾸면서 확인 문구도 실제 동작(캠페인만 목록에서 숨겨지고 링크는 유지)에 맞게 함께 고쳤다.

## 3. 만들지 않은 것 (의도적 축소)

- **프로젝트 개요(KPI 대시보드) 화면**: `04_screen_specs.md` 3장이 제안한 "활성 링크 수 / 활성 캠페인 수 / 최근 7일 클릭 / 눈에 띄는 항목" 요약 화면은 만들지 않았다. 지금 API(`/overview`)는 목록만 반환하고 집계 수치·"만료 임박"·"임포트 실패" 같은 신호를 제공하지 않는다. 실제 데이터 없이 숫자를 꾸며 넣는 것보다, 이 화면은 필요한 집계 API가 생긴 뒤로 미루는 게 맞다고 판단했다.
- **워크스페이스 스위처(드롭다운)**: 현재 사이드바는 최상단에 `srrrg` 로고만 있고, `02_information_architecture.md`가 제안한 "최근 프로젝트 드롭다운 + 검색 + 새 프로젝트 만들기" 스위처는 구현하지 않았다. 프로젝트 전환은 여전히 `/projects` 페이지의 좌측 목록에서 한다.
- **상단 바 검색 / `+ 만들기` 드롭다운**: 상단 바는 페이지 제목과 홈 링크만 가진 최소 구현이다.
- **사이드바 아이콘**: 텍스트 라벨만 사용했다. 아이콘 세트 도입은 `03_visual_system.md` 2절에 남겨둔 대로 보류.

## 4. 후속 작업 후보

- 프로젝트 전체 링크를 가로지르는 검색/필터가 필요해지면, `GET /api/web/projects/{projectId}/links`(커서 페이징, 캠페인/상태 필터) 같은 신규 엔드포인트를 먼저 추가해야 한다.
- 프로젝트 개요 대시보드를 만들려면 "만료 임박 링크 수", "최근 임포트 실패" 같은 신호를 계산하는 백엔드 집계가 먼저 필요하다.
- 링크 상세 드로어는 `aria-modal="false"` + 배경 `inert` 조합으로 만들었다. 배경이 완전히 잠기므로 실질적으로는 모달에 가깝게 동작하지만, 포커스가 드로어 내부를 순환하도록 하는 명시적 focus trap(Tab 키가 드로어 마지막 요소에서 첫 요소로 되돌아가는 것)은 아직 없다.
- 이번 구현은 로컬 환경에서 화면 구조(접근성 트리)만 확인했고, 실제 로그인 세션으로 클릭 흐름 전체를 눈으로 확인하는 QA는 아직 하지 않았다. Phase별 QA 체크리스트는 `05_implementation_qa.md` 5장을 그대로 사용한다.

## 5. Phase 6 조사 결과: 통계 화면은 대부분 이미 정리되어 있었다

`05_implementation_qa.md`가 Phase 6에서 우려한 "캠페인별 비교가 캠페인 상세에도 노출되는 문제"는 실제로는 이미 없었다. `StatisticsService.report()`가 `scope == CAMPAIGN`일 때 `campaigns` breakdown을 아예 빈 페이지(`PageResult.empty()`)로 채우고, 프론트(`srrrg-statistics.js`의 `renderCampaigns`)도 `!page.totalItems`면 섹션을 숨기기 때문에, 캠페인 통계에는 애초에 캠페인 비교 섹션이 나타나지 않는다. 코드 변경 없이 확인만 하고 넘어갔다.

접근성 관련해서는 이번에 새로 만든 컴포넌트(사이드바, 탭, 드로어)에 `role`, `aria-selected`, `aria-controls`, `aria-current`, `aria-live` 등을 처음부터 반영했고, 드로어에는 배경 `inert` 처리를 추가했다(4장 참고).
