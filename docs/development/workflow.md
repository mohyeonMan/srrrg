# 개발 작업 절차

이 문서는 조사, 계획, 승인, 구현과 보고를 분리하여 요청 범위를 통제하는 기준이다.

## 1. 조사

구현 전에 다음을 읽기 전용으로 확인한다.

- AGENTS.md와 작업별 필수 문서
- 관련 코드와 직접·간접 호출 관계
- 관련 테스트와 현재 동작을 설명하는 문서
- git status --short와 대상 파일의 기존 diff

조사 중 관련 문제를 발견해도 요청 범위 밖이면 수정하지 않고 관찰 사항으로만 기록한다.

## 2. 구현계획

계획에는 다음을 빠짐없이 명시한다.

- 요청을 통해 달성할 목표
- 포함할 기능, 계층과 파일
- 명시적으로 제외할 항목
- 수정하거나 새로 만들 예상 파일
- 필요한 선행 작업과 그 이유
- 검증할 명령과 확인할 동작
- 호환성, 데이터, 보안과 운영 위험

요청이 여러 의미로 해석되어 결과나 범위가 달라질 수 있으면 계획을 확정하기 전에 질문한다.
선행 작업이 필요하면 이유, 영향과 가능한 대안을 먼저 제안한다.

## 3. 승인

- 사용자가 계획에 명시적으로 동의하거나 진행을 지시하기 전에는 구현하지 않는다.
- 계획 승인은 적힌 작업만 허용하며 인접 기능이나 후속 개선까지 허용하지 않는다.
- 분석·설명·검토 요청은 파일 변경 권한을 포함하지 않는다.
- 커밋 승인은 push 승인이 아니며, 로컬 변경 승인은 외부 시스템 변경 승인이 아니다.

## 4. 구현

- 승인된 범위만 변경한다.
- 범위 밖 리팩터링, 정리, 기능 추가, 의존성·스키마·배포 설정 변경을 섞지 않는다.
- 구현 중 추가 범위가 필요해지면 즉시 중단하고 발견한 사실, 이유, 영향과 새 범위를 설명해 다시 승인받는다.
- 관련 코드에 기존 사용자 변경이 있으면 보존한다. 안전하게 병합할 수 없으면 작업을 멈추고 알린다.
- 변경한 로직의 주석과 권위 있는 문서는 같은 작업에서 갱신한다.

## 5. Git과 파일 안전

- 작업 시작과 완료 전에 git status --short를 확인한다.
- 사용자 요청 없이 stage, commit, push, branch, tag, stash, rebase, cherry-pick 또는 이력 수정을 하지 않는다.
- git reset --hard, git checkout -- 등 기존 변경을 파괴할 수 있는 명령을 임의로 사용하지 않는다.
- 요청과 무관한 전체 포맷, import 정리, 일괄 치환, 줄바꿈·인코딩 변경을 하지 않는다.
- build/, 성능 결과와 생성 파일을 요청 없이 수정하거나 커밋하지 않는다.
- 대량 기계 변경과 의미 있는 로직 변경을 같은 작업에 섞지 않는다.

삭제나 이동이 필요하면 대상 경로와 영향 범위를 확인하고 계획에 포함한다. 가능한 경우 복구 가능한 방법을 사용한다.

## 6. 비밀정보와 외부 작업

- .env, 인증서, 개인 키, 쿠키와 토큰 원문은 명시적 요청 없이 읽거나 출력하지 않는다.
- 설정 확인은 값 대신 변수명과 존재 여부를 우선 확인한다.
- 출력에 비밀값이 포함될 수 있으면 마스킹하거나 안전한 다른 방법을 사용한다.
- 배포, 메시지 전송, PR 변경과 외부 서비스 쓰기는 계획에 명시하고 별도로 승인받는다.

## 7. 완료 보고

완료 보고에는 다음을 구분하여 적는다.

- 승인된 범위와 실제 변경
- 변경하지 않은 제외 범위
- 실행한 검증 명령과 결과
- 실행하지 못한 검증과 이유
- 발견했지만 수정하지 않은 범위 밖 문제
- 남은 위험과 필요한 후속 결정

완료 보고만으로 새로운 후속 작업을 시작하지 않는다.
