# 구조 설계와 감사 기준

이 문서는 현재 코드의 형태를 정당화하기 위한 기록이 아니라, 현재 구조를 평가하고 목표 구조를 결정하는 독립적인 기준이다.
특정 아키텍처 이름이나 파일 크기보다 책임, 변경 이유, 의존성 방향과 도메인 소유권을 평가한다.

## 1. 메서드

- 메서드는 이름으로 설명할 수 있는 하나의 역할만 수행한다.
- 줄 수는 분리 여부의 기준으로 사용하지 않는다.
- 일부 코드가 메서드 이름이 나타내는 역할을 벗어나면 짧더라도 분리한다.
- 서로 다른 이유로 변경되는 로직과 서로 다른 생명주기·실패 정책을 요구하는 로직은 분리한다.
- 하나의 메서드 안에서 업무 정책과 저수준 구현 세부사항의 추상화 수준을 불필요하게 섞지 않는다.
- 분리된 메서드는 독립적인 의미가 있는 이름을 가져야 한다.
- 줄 수만 줄이는 단순 위임이나 호출 추적만 늘리는 분리는 하지 않는다.

판단 질문은 “이 코드가 변경되는 이유가 메서드의 나머지 코드와 같은가”이다.

## 2. 클래스와 파일

- 클래스는 응집된 하나의 책임과 변경 이유를 가진다.
- 권한 판정, 업무 정책, 외부 통신, 저장과 표현 책임이 한 클래스에 섞였는지 검토한다.
- 여러 메서드가 같은 상태와 규칙을 공유하고 독립적으로 변경될 수 있으면 별도 클래스로 분리한다.
- 구현체 하나만 위한 인터페이스나 단순 위임만 하는 껍데기 계층을 만들지 않는다.
- 독립적인 최상위 타입은 하나의 파일에 둔다.
- 독립적으로 이름을 붙이거나 테스트·재사용할 의미가 있는 타입은 내부 클래스에 두지 않는다.
- 내부 클래스·익명 클래스·중첩 record는 바깥 타입의 구현 세부사항이며 독립적인 도메인 의미가 없을 때만 사용한다.

## 3. 패키지와 도메인

- 클래스는 기술 계층보다 핵심 업무 도메인을 기준으로 배치한다.
- 여러 도메인을 조율하는 클래스는 흐름을 소유하는 도메인에 둔다.
- 두 도메인에 모두 속해 보이면 common으로 옮기기 전에 책임 분리를 검토한다.
- util, helper, common, service.impl을 책임이 불명확한 수납 공간으로 사용하지 않는다.
- common에는 여러 도메인이 안정적으로 공유하는 기술 책임만 둔다.
- 패키지 이름과 클래스 이름만으로 소유 도메인과 역할을 추론할 수 있어야 한다.

## 4. 계층과 의존성

- Controller는 HTTP 계약과 인증 주체 변환을 담당하고 업무 정책을 직접 소유하지 않는다.
- Service는 유스케이스와 업무 흐름, 권한과 트랜잭션 경계를 조율한다.
- Entity는 자신의 상태와 직접 관련된 불변조건을 보호한다.
- Repository는 데이터 접근 의미를 표현하며 업무 흐름을 조율하지 않는다.
- 의존성 방향은 일관되어야 하며 순환 의존을 허용하지 않는다.
- 기술 프레임워크와 외부 시스템 세부사항이 핵심 업무 정책으로 불필요하게 전파되지 않아야 한다.
- Controller의 Repository 직접 호출 같은 예외는 편의가 아니라 명확한 근거와 제한된 범위를 가져야 한다.

## 5. 횡단 관심사

- 트랜잭션, 보안, 예외 변환, 로깅, 메트릭과 캐시는 각 업무 흐름에서 경계와 책임이 명확해야 한다.
- 외부 호출과 DB 트랜잭션의 생명주기를 불필요하게 결합하지 않는다.
- 인증 방식이 다른 API 표면도 공통 업무 규칙을 중복 구현하지 않는다.
- 실패 정책과 관찰 가능성 때문에 업무 코드가 과도하게 분기된다면 별도 책임으로 분리할 수 있는지 검토한다.

## 6. 변경 용이성

구조가 적절한지는 다음 변경 시나리오로 확인한다.

- 권한 정책 하나를 바꿀 때 몇 개의 패키지와 경로를 수정해야 하는가
- 새로운 인증 또는 API 표면을 추가할 때 업무 규칙이 복제되는가
- URL 위험 검사, UTM 또는 캠페인 정책 변경이 HTTP·DB 세부사항과 함께 번지는가
- 링크 유형을 추가할 때 기존 조건 분기가 여러 클래스에 반복되는가
- 변경 하나를 안전하게 검증하기 위해 지나치게 큰 fixture가 필요한가

같은 이유로 바뀌는 코드는 함께 있고, 다른 이유로 바뀌는 코드는 분리되어야 한다.

## 7. 구조 감사 방법

1. 이 문서의 기준을 감사 전에 확정한다.
2. 패키지, 클래스, 생성자 의존성, 호출 관계와 트랜잭션 경계를 조사한다.
3. 기준 위반과 현재 제약상 합리적인 예외를 구분한다.
4. 모든 판단에 파일, 클래스, 메서드와 구체적인 변경 위험을 근거로 제시한다.
5. 문제의 심각도, 확신도, 영향 범위와 최소 개선 방향을 기록한다.
6. 현재 구조를 기준에 맞추기 위해 필요한 목표 패키지·클래스 구조와 단계별 우선순위를 제안한다.
7. 사용자 승인 전에는 감사 결과를 구현하거나 리팩터링하지 않는다.

파일 크기, 메서드 수와 의존성 수는 조사 후보를 찾는 지표일 뿐 문제를 확정하는 기준으로 사용하지 않는다.
