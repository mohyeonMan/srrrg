# 정보구조 재편 기록

프로젝트·캠페인·링크 세 레벨의 탭 문법을 통일하는 작업의 진행 기록입니다.
판단 근거는 `docs/desktop-audit.md`(데스크톱 실측)와 아래 측정값입니다.

## 목표 구조

| 레벨 | 탭 | 생성 |
| --- | --- | --- |
| 프로젝트 | `개요` / `멤버` / `UTM` / `설정` | 헤딩 CTA → 대화상자 |
| 캠페인 | `개요` / `링크` / `만들기` / `설정` | 탭 유지(대량 생성 작업공간) |
| 링크 | `통계` / `링크 설정` | — (변경 없음) |

캠페인의 생성 탭을 유지하는 이유: 동적 UTM 입력 + 이동 주소 미리보기 + CSV 대량 생성
(최대 10,000행·10MB, 오류 CSV 다운로드)을 담은 **머무는 작업공간**이라 대화상자에 맞지 않습니다.
프로젝트 레벨의 두 생성은 필드 3~4개로 끝나는 단발 작업입니다.

원칙: **탭 = 머무는 작업공간, 대화상자 = 한 번에 끝나는 생성.**

## Phase 0 — 선행 조건 (완료)

IA 는 바꾸지 않고, 재편이 기능 후퇴 없이 가능하도록 바닥을 깔았습니다.

### 0.1 모바일 탭 라벨 실측 (320px, `/manage` 의 실제 `.console-tabs` 기준)

폰트 `600 14px`, 스트립 좌우 패딩 24px, 셸 300px.

| 탭 수 | 탭 1개당 예산 |
| --- | --- |
| 2 | 134px |
| 3 | 87px |
| **4** | **63px** |
| 6 | 39px |

| 라벨 | 실측 폭 | | 라벨 | 실측 폭 |
| --- | --- | --- | --- | --- |
| 개요 · 멤버 · 설정 · 링크 · 통계 | 28px | | 링크 목록 · 링크 생성 · 멤버 관리 · 링크 설정 | 61px |
| UTM | 32px | | UTM 관리 | 65px |
| 만들기 | 42px | | 캠페인 생성 | 75px |

판정:

- **목표 구조(4탭, 짧은 이름)**: 최대 32px vs 예산 63px → 여유 31px. 성립.
- **`~관리` 접미사**: `UTM 관리` 65px > 63px → 줄바꿈. **짧은 이름이 선택이 아니라 필수.**
- **생성을 탭에 넣는 안(6탭)**: `캠페인 생성` 75px vs 예산 39px → 약 2배 초과. **기각.**
  갭을 8px 로 줄인 뒤에도 성립하지 않으므로 이 기각은 견고합니다.
- **현재 캠페인 4탭**: `링크 목록` 61px. 갭이 24px 이던 동안 예산이 51px 이었으므로
  **320px 에서 실제로 줄바꿈하고 있었습니다.** 0.2 로 예산이 63px 이 되어 해소됐고,
  여유가 2px 뿐이라 Phase 3 의 라벨 축약(`링크` 28px, `만들기` 42px)이 실질적 의미를 갖습니다.

### 0.2 좁은 폭 탭 갭 축소 (24px → 8px)

`.console-tab { flex: 1 }` 로 탭이 균등 분할되는 폭에서 24px 갭은 과했습니다.
320px 4탭이면 스트립 276px 중 **갭만 72px(26%)** 를 먹어 라벨 예산이 51px 로 눌렸습니다.
`--space-2`(8px)로 줄여 63px 확보. 위 판정대로 **기존 줄바꿈 결함이 함께 해소**됐습니다.

### 0.3 탭 컨트롤러 공용화 + 주소화

`srrrg-campaigns.js` 와 `srrrg-projects.js` 가 같은 코드를 각자 갖고 있었습니다 —
`{prefix}-tab-{name}` / `{prefix}-panel-{name}`, roving tabindex, 좌우 순환 방향키까지 동일.
`SrrrgCommon.tabs({ list, prefix, param, initial })` 하나로 합쳤습니다.

추가된 것:

- `?tab=<name>` 동기화. `location.hash` 는 `ProjectsPageAssetTest` 가 금지하므로 쿼리 파라미터를 씁니다.
- 목록에 없는 `initial` → 첫 탭 폴백.
- 버튼·패널이 없는 이름은 예외 없이 건너뜀(`srrrg-projects.js` 가 의존했던 관용성).

**URL 은 사용자가 탭을 누를 때만 씁니다.** 초기 bind 에서는 쓰지 않습니다 —
아무것도 바뀌지 않은 시점에 주소를 더럽히지 않고, 두 묶음이 동시에 초기화되는 경우의
덮어쓰기 경합도 원천적으로 없앱니다. **`replaceState`** 를 씁니다: 탭 전환은
히스토리에 쌓일 사건이 아니고, 뒤로가기가 탭을 되짚는 대신 이전 화면으로 나가는 편이 예측 가능합니다.

`srrrg-management.js`(링크 레벨)의 탭은 **합치지 않았습니다.** ID 규칙이 다르고
(`analytics-tab`), 비활성 탭을 건너뛰며, 저장 안 된 변경이 있으면 확인 대화상자를 띄우는
`requestTab` 게이트가 있습니다. 게다가 그 화면은 secret key 게이트 뒤라 주소를 공유해도
열리지 않으므로 URL 동기화의 이득이 없습니다. 억지로 합치면 옵션만 늘고 얻는 게 없습니다.

두 묶음이 섞일 걱정은 템플릿 차원에서 이미 없습니다. `projects.html` 의 `th:if` 가
프로젝트 탭 스트립을 `campaignId == null and linkCode == null and view ∉ {utm-templates, project-settings}`
일 때만 렌더하므로, 프로젝트 스트립이 있을 때는 캠페인 스트립이 없습니다.
초기값 판정에 별도 가드를 두었다가 이 사실을 확인하고 **죽은 코드라서 제거**했습니다.

### 0.4 패널 지연 초기화 — Phase 2 로 미룸

원래 Phase 0 에 넣었다가 뺐습니다. Phase 0 은 어떤 패널이 렌더되는지 바꾸지 않으므로
지연 초기화가 필요한 시점이 아닙니다. 지금 만들면 쓰이지 않는 코드입니다.

**Phase 2 에서 반드시 필요해집니다:** 설정·UTM 조각을 `th:if` 없이 상시 렌더 탭 패널로
바꾸는 순간, `projects.html` 이 이미 8개 스크립트를 무조건 로드하고 있으므로
`srrrg-project-settings.js` 와 `srrrg-project-utm-templates.js` 의 `if (!app) return` 가드가
풀려 **프로젝트 페이지 로드마다 API 2건이 추가로 발생**합니다. 그중 설정 쪽 `loadProject()` 는
`srrrg-projects.js` 가 이미 가진 데이터를 중복 조회합니다.
기존 선례(`window.SrrrgProjectMembers?.reload(...)`)를 그대로 확장하면 됩니다.

### 검증

- 전체 테스트 226건 통과(실패 0, 오류 0, 건너뜀 34)
- 컨트롤러 기능 검사 11건 통과: 초기 페인트(`aria-selected`/`tabIndex`/`hidden`),
  초기 bind 의 URL 미기록, 클릭 시 URL 기록, 좌우 방향키 순환(양방향),
  `initial` 존중, 알 수 없는 값 폴백, 패널 누락 관용, `replaceState`(히스토리 미증가)
- 탭·패널 ID 짝 1:1 확인(캠페인 4쌍 / 프로젝트 2쌍), 중복 ID 없음
- 공개 화면 콘솔 오류 0건
- 순 변경량 +78/−58 (중복 구현 2개 → 공용 1개, 그러면서 URL 동기화와 관용성이 추가됨)

### 남은 확인 (Phase 0)

Chrome 확장이 이번 라운드 중간에 끊겨 **로그인 상태의 프로젝트·캠페인 화면에서
탭을 실제로 눌러보는 검증은 하지 못했습니다.** 컨트롤러 로직은 격리 검사 11건과
전체 테스트로 확인했고, 서버가 내보내는 HTML 의 ID 짝도 확인했습니다.
프로젝트 화면에서 아래만 눌러봐 주시면 Phase 0 은 마감됩니다.

1. 프로젝트 개요에서 `통계` ↔ `멤버` 전환 → 주소에 `?tab=members` 가 붙는지
2. 그 주소를 새로 열었을 때 `멤버` 탭으로 복원되는지
3. 캠페인에서 `개요`/`링크 목록`/`링크 생성`/`설정` 전환과 좌우 방향키
4. 캠페인 링크가 0개일 때 "만들기로 이동" 버튼이 `링크 생성` 탭으로 넘기는지
5. 320px 에서 캠페인 4탭 라벨이 한 줄로 보이는지

사용자 육안 확인 완료(정상). Phase 0 마감.

## Phase 1 — 레일 종 분리와 생성 대화상자 (완료)

탭 구조는 건드리지 않고, 생성이 화면을 파괴하는 문제와 레일의 종 혼합을 해결했습니다.

### 1.1 생성을 헤딩 CTA + 대화상자로

이전에는 레일의 `단축링크 생성` / `캠페인 생성` 을 누르면 `view=create-link|create-campaign` 상태가 되고
`showProjectPanel()` 이 요약(`#project-home-panel`)과 탭 바(`#project-view-tabs`)를 함께 숨겼습니다.
**무언가를 만들려고 누르면 보고 있던 화면과 프로젝트의 지도가 사라졌습니다.**

`#create-link-dialog` / `#create-campaign-dialog` 두 대화상자로 옮겼습니다.
새 컴포넌트를 만들지 않고 `#create-project-dialog` 가 이미 쓰던 `<dialog>` + `.project-create-dialog` 패턴을 그대로 씁니다.
폼의 모든 ID 를 유지해 검증·만료 옵션·결과·복사 동작은 손대지 않았습니다.

**계획에서 바꾼 것 — 레일의 생성 항목은 남기지 않고 삭제했습니다.**
계획에는 "레일 shortcut 으로 남긴다" 고 적었는데, `.projects-heading` 이 `.projects-layout`
**바깥**이라 캠페인·링크·설정 어느 화면에서도 보인다는 것을 확인했습니다.
헤딩 CTA 가 이미 어디서든 1클릭이므로 레일에 같은 것을 둘 이유가 없습니다.
(shortcut 이 평탄함을 지킨다는 근거는 탭으로 들어갈 `UTM`·`설정` 에만 적용됩니다.)

`＋ 만들기 ▾` 메뉴 대신 **버튼 두 개**로 갔습니다. 열고닫기 상태·외부 클릭 처리·메뉴 키보드 의미가
전부 불필요해지고, 좁은 폭 문제는 `flex-wrap` 으로 해결됩니다.

### 1.2 레일의 종(種) 분리

레일의 네 항목은 모두 `.project-activity-item` 이었습니다 — **아래 콘텐츠 목록의 캠페인 항목과 같은 클래스**로,
동작(만들기)·섹션(UTM·설정)·객체(캠페인)가 한 열에서 구분되지 않았습니다.
생성 둘은 헤딩으로 옮기고, 남은 둘은 `.project-rail-shortcut` 으로 분리해 26px 글리프 배지를 버렸습니다.

### 1.3 함께 정리한 죽은 코드

- `showProjectPanel()` 전체 — 세 상태를 오갈 일이 없어졌고, 남은 것은 템플릿 기본 상태와 탭 컨트롤러 소관
- `state.canEdit` 대입 — 읽는 곳이 `showProjectPanel()` 뿐이었음
- `.project-activity-kind.template` / `.settings` — 활동 목록은 `campaign`·`link` 만 내보냄
- `.project-link-create` (브랜드색 상단 테두리) — 그 판이 사라짐
- `focusOpenedPanel()` 의 대화상자 제목 두 개 — 대화상자는 항상 DOM 에 있어 그대로 두면
  알 수 없는 `view` 값에서 숨은 제목으로 포커스가 갔음. 포커스는 `<dialog>` 가 관리

### 1.4 작업 중 발견해 고친 결함 2건

**결함 A — 대화상자를 `#project-detail` 안에 두면 렌더되지 않는다.**
처음에 판이 있던 자리에 그대로 대화상자를 넣었는데, `#project-detail` 은 캠페인·링크·설정 화면에서
`hidden`(= `display: none`)이 됩니다. `display: none` 조상 아래의 `<dialog>` 는 `showModal()` 해도
렌더되지 않습니다. 페이지 수준(`#confirm-dialog` 옆)으로 옮겼고,
**테스트에 문서 순서 단정을 넣어** 다시 안으로 들어가면 실패하게 했습니다.

**결함 B — 420px 대화상자에서 만료 옵션 라벨이 줄바꿈된다.**
`.expire-options` 기본값은 `repeat(6, minmax(0, 1fr))` 이고, 열 수를 줄이는 미디어쿼리는
**뷰포트**를 봅니다 — 데스크톱 뷰포트에서 이 폼이 420px 대화상자 안에 있다는 걸 알 수 없습니다.

| | 열 | 버튼 폭 | `직접 입력` |
| --- | --- | --- | --- |
| 옮긴 직후 | 6열 | 56px | **2줄** |
| `auto-fit` 적용 | 4열 2행 | 89px | 1줄 |

`#create-link-dialog .expire-options` 로 **이 대화상자에만** `repeat(auto-fit, minmax(76px, 1fr))` 을 걸었습니다.
공용 컴포넌트 기본값과 홈의 생성 도구는 건드리지 않았습니다(홈 실측: 여전히 6열 106px, 전부 1줄).

`scrollWidth` 로는 이 결함이 잡히지 않습니다 — 줄바꿈은 넘침이 아니기 때문입니다.
`Range.getClientRects().length` 로 실제 줄 수를 세어 확인했습니다(320px 헤더 로그인 버튼과 같은 함정).

### 1.5 헤딩 CTA 의 좁은 폭 동작

`.projects-heading` 에 `flex-wrap: wrap` + `gap` 을 주어 CTA 가 제목을 눌러 줄이지 않고 아래 줄로 갑니다.
다만 320px 에서 두 버튼이 필요 폭보다 **1px 모자라** 우연히 2줄로 쌓였습니다 — 라벨이 조금만 바뀌어도
한 줄/두 줄이 뒤집히는 상태였습니다. `@media (max-width: 520px)` 에서 컨테이너를 전폭으로 두고
버튼에 `flex: 1` 을 주어 **의도된 한 줄**(각 146px)로 고정했습니다.

### 검증

- 전체 테스트 226건 통과(실패 0). 새 단정: 대화상자 ID·CTA·shortcut 클래스,
  인라인 판 부재, **대화상자가 `#project-detail` 보다 앞에 있음**
- 서버 렌더 HTML 확인: `create-link-dialog`(4684) / `create-campaign-dialog`(7700) 모두
  `project-detail`(10855) 앞. 구 ID 4개 모두 제거됨
- 태그 균형(dialog 4/4, section 9/9, form 3/3 등), CSS 중괄호 균형
- 만료 옵션 before/after 실측(위 표), 홈 미영향 실측
- 헤딩 CTA 1280px 1행 / 320px 전폭 1행 146px, 가로 넘침 없음
- 콘솔 오류 0건

### 남은 확인 (Phase 1, 로그인 필요)

Chrome 확장이 계속 연결되지 않아 로그인 상태의 실제 클릭은 확인하지 못했습니다.

1. 헤딩의 `링크 만들기` → 대화상자가 열리고 원본 URL 칸에 포커스가 가는지
2. 링크 생성 성공 → 대화상자 안에 단축 URL + 복사 버튼이 나오고, 닫으면 **보고 있던 탭이 그대로**인지
3. 두 번째로 열었을 때 지난 결과·메시지가 지워져 있는지
4. `캠페인 만들기` → 성공 후 만든 캠페인 화면으로 이동하는지
