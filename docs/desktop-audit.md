# 데스크톱 전면 재검수 (1280 / 1440 / 1920)

모바일 재검수(`docs/mobile-audit.md`)와 같은 절차를 데스크톱 폭에서 수행한 기록입니다.
수치는 모두 실행 중인 브라우저에서 실측한 값이고, 판단 근거가 캡처인 항목은 그렇게 밝혔습니다.

## 0. 검증 방법과 그 한계

### 0-1. 데스크톱은 1024px 위에서 레이아웃이 한 종류다

`static/css/srrrg/*.css` 전체의 미디어쿼리 상한을 뽑으면
380 / 520 / 560 / 640 / 720 / 860 / 900 / 980 / 1023 + `prefers-reduced-motion` 뿐입니다.
**1023px 위에는 분기가 없습니다.** 따라서 1280·1440·1920 은 콘텐츠 기하가 동일하고
가운데로 모으는 여백만 커집니다. 이 사실이 아래 두 가지를 정당화합니다.

- 세 폭을 따로 캡처해도 콘텐츠는 같으므로, 폭별 차이는 여백·정렬축·줄바꿈에서만 본다.
- 로그인 세션이 있는 브라우저의 뷰포트를 넓힐 수 없을 때,
  셸 폭을 상한값으로 고정하면 실제 넓은 뷰포트의 콘텐츠 기하가 그대로 재현된다.

### 0-2. 도구별 신뢰 범위 (이번에 다시 확인)

| 도구 | 뷰포트 변경 | 캡처 | 측정 | 세션 |
| --- | --- | --- | --- | --- |
| 인앱 브라우저 | 가능 | 320px 는 1:1, 1280px 부터는 균일 축소(0.27배) + 빈 캔버스 | 정확 | 없음 |
| Chrome | **거부**(`Bounds must be at least 50% within visible screen space`, `outerWidth: 0`) | 정확 | 정확 | 있음 |

인앱 캡처가 작게 나오는 것은 **균일 축소**임을 이번에 확인했습니다.
1280px 에서 페이지가 캔버스의 좌상단 27% 를 차지하고 가로·세로 배율이 같았습니다.
이전 라운드에서 "빈 띠가 보인다" 고 의심했던 것은 이 빈 캔버스였고, CSS 결함이 아닙니다.

`zoom` 으로 Chrome 의 레이아웃 뷰포트를 넓히려는 시도는 실패했습니다.
`documentElement.style.zoom = 0.55` 는 레이아웃 폭을 넓히지 않고 축소만 하며
(`shellW` 1032 → 682), 미디어쿼리도 그대로였습니다.

### 0-3. 실제로 검증하지 못한 것

로그인한 화면을 **1280·1440·1920 뷰포트에서 직접 캡처**하지는 못했습니다.
세션이 있는 브라우저는 리사이즈가 거부되고, 리사이즈되는 브라우저에는 세션이 없습니다.
대신 세션이 있는 Chrome 에서 셸 폭을 상한으로 고정해 **측정**했습니다 —
0-1 의 이유로 기하는 동일하지만, 캡처가 아니라 측정이라는 점을 밝힙니다.

`--panel-padding` 은 `clamp(18px, 2.2vw, 24px)` 이므로 고정 측정 환경(뷰포트 1064)에서 23.4px,
실제 1091px 이상에서는 24px 로 고정됩니다. 아래 좌표의 23.4/25 는 실제 데스크톱에서 24/25 입니다.

### 0-4. 로그인 검수 (미완)

요청한 순서 중 3단계에서 멈췄습니다. 로그인 → Google로 계속까지 진행하면
Google 이 **계정 선택 화면이 아니라 이메일·비밀번호 입력 폼**("이메일 또는 휴대전화")을 띄웁니다.
자격증명을 대신 입력하지 않는다는 원칙에 따라 여기서 중단했고, 페이지는 그대로 두었습니다.
`qkrwlgns0510@gmail.com` 을 직접 선택해 주시면 이후 화면은 이어서 검수할 수 있습니다.

로그인 **화면 자체**(`/login`)와 로그아웃 상태 헤더는 아래 6절에서 검수했습니다.

## 1. 정렬축: 헤더와 본문이 서로 다른 축에 서 있었다

### 발견

| 뷰포트 | 워드마크 x | 본문 x | 어긋남 |
| --- | --- | --- | --- |
| 1920 | 28 | 400 | **372px** |
| 1440 | 28 | 160 | **132px** |
| 320 | 20 | 10 | **10px** |

헤더는 `padding: … clamp(16px, 3vw, 28px)` 라는 **고정 여백**을 쓰고 있었고,
본문 셸은 `min(1240px, 100% - 32px)` 로 **가운데 정렬**이었습니다.
넓은 화면에서 본문이 가운데로 모이는 동안 워드마크는 왼쪽 끝에 박혀 축이 벌어졌습니다.

셸마다 폭 식이 따로 적혀 있던 것이 근본 원인이었습니다.

| 셸 | 이전 폭 | 좁은 폭 재정의 |
| --- | --- | --- |
| `.page-shell` (홈·계정·온보딩) | `min(1120px, 100%-32px)` | ≤860 `min(100%-24px, 720px)`, ≤520 `100%-20px` |
| `.projects-shell` | `min(1240px, 100%-32px)` | ≤520 `100%-20px` |
| `.management-shell` | `min(1240px, 100%-32px)` | ≤640 `100%-20px` |

같은 화면 전환에서 정렬축이 60px(1240 vs 1120), 브레이크포인트마다 12px·10px 씩 움직였습니다.

### 수정

폭과 여백을 **한 쌍의 토큰에서** 계산하도록 바꿨습니다(`base.css`).

```css
--shell-max: 1360px;
--shell-gutter: 16px;
--shell-width: min(var(--shell-max), calc(100% - var(--shell-gutter) * 2));
--shell-inset: calc((100% - var(--shell-width)) / 2);
```

- 모든 셸: `width: var(--shell-width)`
- 헤더: `padding-inline: var(--shell-inset)` (띠 자체는 전폭 유지 → 테두리가 끝까지 이어진다)
- 좁은 폭: `responsive.css` 의 `@media (max-width: 640px)` 에서 `--shell-gutter: 10px` **하나만** 재정의

헤더 여백과 셸 위치가 **같은 식**이 되었으므로 등호는 우연이 아니라 구조적으로 성립합니다.

`.page-shell` 의 ≤860 폭 상한(720px)과 헤더의 좌우 패딩 재정의(24px, 20px)는 삭제했습니다.
읽는 문단은 각자 `max-width` 로 이미 제한됩니다(홈 인트로 480px — 768px 에서 실측 확인).

### 검증 (실측, 좌우 양쪽)

| 뷰포트 | gutter | 헤더 여백 | 셸 위치 | 셸 폭 | 좌 어긋남 | 우 어긋남 | 가로 넘침 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1920 | 16 | 280 | 280 | 1360 | **0** | **0** | 없음 |
| 1440 | 16 | 40 | 40 | 1360 | **0** | **0** | 없음 |
| 1280 | 16 | 20 | 20 | 1240 | **0** | **0** | 없음 |
| 1024 | 16 | 16 | 16 | 992 | **0** | **0** | 없음 |
| 768 | 16 | 16 | 16 | 736 | **0** | **0** | 없음 |
| 430 | 10 | 10 | 10 | 410 | **0** | **0** | 없음 |
| 320 | 10 | 10 | 10 | 300 | **0** | **0** | 없음 |

모바일(320·430)도 이전 −10px 에서 0 으로 개선됐습니다. 모바일 수정을 되돌리지 않고 함께 맞췄습니다.

## 2. 빈 공간과 밀도: 상한 1240 → 1360

### 근거

1920px 에서 좌우 여백이 화면의 **42%**(1120 상한) 였습니다. 상한을 통일해도 35% 였습니다.

밀도 쪽 근거를 같이 봤습니다. 캠페인 링크 표에 현실적인 장문
(캠페인 이름 "2026 여름 시즌 신규 가입 프로모션 A안", 목적지
`https://shop.example.co.kr/landing/summer-2026/signup?variant=a&ref=partner")을 넣고 상한별 행 높이를 실측했습니다.

| 셸 상한 | 콘텐츠 칼럼 | 표 가용 | 행 높이(장문) |
| --- | --- | --- | --- |
| 1240 | 930 | 879 | **86px** |
| 1360 | 1050 | 999 | **78px** |
| 1440 | 1130 | 1079 | 67px |

표는 `width: 100%` + `min-width: 640px` 이므로 항상 가용 폭을 채웁니다.
(초기에 "가용 881 / 필요 879 = 여유 2px" 로 읽고 빡빡하다고 판단했는데, 이는 오독이었습니다.
유동 표에서 `needed == visible` 은 여유 없음이 아니라 정상입니다. 실제 신호는 **줄바꿈으로 인한 행 높이**였습니다.)

### 결정: `--shell-max: 1360px`

- 1920px 여백 비중 35% → **29%**
- 장문 행 높이 86px → **78px**
- 1440px 노트북에서 좌우 40px 이 남는다

1440px 로 더 넓히지 않은 이유: 1440px 화면에서 좌우 여백이 16px 만 남아 본문이 화면에 붙습니다.
가장 흔한 데스크톱 폭에서 여백이 사라지는 대가가 행 높이 11px 보다 큽니다.

홈 히어로는 1920px 에서 508 / 795 두 칼럼이 되고, 인트로 문단은 `max-width: 480px` 로 계속 제한됩니다.

## 3. 화면 안 정렬축: 4px·8px 씩 어긋난 판들

콘텐츠 칼럼 기준 본문 왼쪽 좌표를 모아 보면, 한 화면에 축이 세 개씩 있었습니다.

### 발견 (캠페인 통계 화면, 콘텐츠 칼럼 기준)

| 좌표 | 무엇 | 원인 |
| --- | --- | --- |
| 25 | `.console-header` / `.campaign-workspace-header` 본문 | `--panel-padding` (24) + 테두리 1 |
| 21 | `.analytics-section` 본문·표 | `--space-5` (20) + 1 |
| 17 | `.metric-item` 지표 라벨 | `--space-4` (16) + 1 |

같은 성격의 판인데 여백만 4px·8px 다릅니다. 극적인 파괴는 아니지만
"정돈된 전문가의 작업대" 가 아니라 손이 덜 간 화면으로 읽히는 종류의 어긋남입니다.

같은 원인을 화면별로 더 찾았습니다.

| 클래스 | 이전 좌우 여백 | 화면 |
| --- | --- | --- |
| `.analytics-section` | `--space-5` | 통계 |
| `.metric-item` | `--space-4` | 통계 |
| `.project-summary` | `--space-5` | 프로젝트 개요 |
| `.project-switcher` | `--space-5` | UTM 템플릿 |
| `.danger-zone` (management.css 사본) | `--space-5` | 프로젝트 설정 |

### 수정

판 성격의 표면은 좌우를 모두 `--panel-padding` 으로 맞췄습니다.
타일(`.metric-item`)과 한 줄 요약(`.project-summary`)은 **위아래만** 좁게 유지했습니다
(`padding: var(--space-4) var(--panel-padding)`) — 세로 밀도는 타일답게, 가로 축은 판과 함께.

버튼·레일 내부·모달·중첩 상자의 좁은 여백은 그대로 뒀습니다. 판이 아니기 때문입니다.

### 검증 (셸 1360 고정, 콘텐츠 칼럼 1050)

| 화면 | 이전 축 | 이후 축 | 겹침 | 잘림 | 24px 미만 타깃 | 데스크톱 카드화 |
| --- | --- | --- | --- | --- | --- | --- |
| 프로젝트 개요 | 0 / 21 / 25 / 49 | **25 / 50** | 0 | 0 | 0 | 0 |
| 프로젝트 개요 · 멤버 | — | 0 / 25 | 0 | 0 | 0 | 0 |
| 프로젝트 설정 | 0 / 21 / 25 | **0 / 25 / 26** | 0 | 0 | 0 | 0 |
| UTM 템플릿 | 0 / 21 / 25 | 0 / 25 | 0 | 0 | 0 | 0 |
| 캠페인 개요 | — | **25** (단일) | 0 | 0 | 0 | 0 |
| 캠페인 링크 목록 | 17 / 21 / 25 | 25 / 26 | 0 | 0 | 0(간격 예외) | 0 |
| 캠페인 링크 생성 | — | 25 | 0 | 0 | 0(간격 예외) | 0 |

25 와 26 은 같은 축입니다(테두리 1px vs `.danger-zone` 좌측 마커 2.2px).
50 은 `.console-panel` 안에 `.analytics-section` 이 들어가는 2단 중첩으로,
각 단이 `--panel-padding` 한 걸음씩 깊어지는 의도된 위계입니다(드리프트가 아님).

## 4. `.danger-zone`: 주석이 설명하는 디자인이 지고 있었다

### 발견

`components.css` 는 이렇게 적어 두었습니다 — "면 전체를 붉게 칠하면 화면 아래쪽이 항상 경고처럼
보이므로 중립 면에 좌측 마커만 둔다". 그런데 실제로는 **사방이 danger 색 테두리**로 둘러져 있었습니다.

원인은 캐스케이드 충돌입니다. `srrrg.css` 의 `@import` 목록에 `management.css` 가 없고,
페이지가 `srrrg.css` **뒤에** 따로 불러옵니다. 같은 `.danger-zone` 이 두 파일에 있어
뒤에 실리는 `management.css` 쪽(사방 danger 테두리, 여백 20px)이 이겼습니다.

두 번째 발견: 카드형 사용처 두 곳의 마크업이 달랐습니다.

```html
<!-- management.html: 제목+설명을 div 로 묶음 (올바름) -->
<div><h3>링크 삭제</h3><p>…</p></div><button>…</button>

<!-- project-settings.html / campaigns.html: 형제로 나열 -->
<h3>프로젝트 삭제</h3><p class="help-text">…</p><button>…</button>
```

`.danger-zone` 이 flex 였으므로 형제 셋이 **각각 칼럼**이 되어, 제목(x=21)과
그 제목을 설명하는 문장(x=213) 사이에 **98px 의 빈칸**이 생겼습니다. 실측한 좌표입니다.

### 수정

1. 본체 정의를 `components.css` 한 곳으로 합치고 `management.css` 의 사본을 삭제.
   단독 사용처(`management.html`)가 있으므로 판 속성을 스스로 갖게 했습니다.
2. `project-settings.html` / `campaigns.html` 의 제목+설명을 `<div>` 로 묶음.
3. 레이아웃을 flex → **grid** 로. `.project-card { display: grid }` 가 `projects.css`
   (= `components.css` 보다 뒤)에서 이기기 때문에 flex 는 매번 무력화됩니다.
   `grid-template-columns: minmax(0, 1fr) auto` 는 그 grid 와 싸우지 않고 함께 동작합니다.
   좁은 폭 규칙도 `flex-direction: column` → `grid-template-columns: minmax(0, 1fr)` 로 교체.

캐스케이드를 `!important` 나 선택자 가중치로 이기지 않고, 뒤에 오는 규칙과 **협력하는** 속성으로 바꿨습니다.

### 검증 (실측)

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 테두리 | 사방 `rgb(242,201,198)` | 중립 `rgb(227,231,236)` + 좌측 2.2px danger |
| 좌우 여백 | 20px | 23.4px (판 공통 축) |
| 자식 배치 | 제목 21 / 설명 **213** / 버튼 676 | 텍스트 덩어리 26 / 버튼 우측 672 |
| 제목·설명 좌표 | 21, 213 (어긋남) | **26, 26** (일치) |

## 5. 클릭 영역·포커스·키보드

### 5-1. 표 안 링크가 글자 높이만큼만 눌렸다

`.activity-table` 셀의 링크(캠페인 이름 등)가 **17px** 높이였습니다. 셀 패딩이 만드는 행 높이(45px)와
클릭 가능한 범위가 달랐습니다.

```css
.activity-table td a { display: inline-block; padding-block: 4px; }
```

17 → **25px**. WCAG 2.5.8 의 24px 를 자체로 넘겨 간격 예외에 기대지 않습니다.
셀 패딩이 이미 행 높이를 만들고 있어 표는 늘어나지 않았습니다.
프로젝트 개요의 24px 미만 타깃 수: **2건 → 0건**.

### 5-2. 남은 작은 타깃은 간격 예외로 통과 (수치 확인)

| 타깃 | 높이 | 가장 가까운 타깃까지 | 판정 |
| --- | --- | --- | --- |
| 헤더 워드마크 | 20~22px | 75~625px | 통과 |
| 링크 관리 열기 | 23px | 73px | 통과 |
| API 문서 보기 / OpenAPI JSON | 22px | 73~121px | 통과 |
| 표 행 체크박스 | 20px | 127px | 통과 |

`.checkbox-row` 의 20px 체크박스는 이를 감싸는 **`<label>` 이 1001×44** 이므로
실제 타깃은 44px 입니다. `<input>` 크기는 타깃 경계가 아닙니다.

### 5-3. 레일 칩의 키보드 포커스가 사실상 보이지 않았다

```css
/* 이전 */
.project-activity-controls button:hover,
.project-activity-controls button:focus-visible { …; outline: none; }
```

hover 와 한 규칙으로 묶여 `outline: none` 이 포커스에도 적용됐고,
키보드 포커스가 **1px 테두리 색 변화**만으로 표시돼 WCAG 2.4.11 을 만족하지 못했습니다.
`outline: none` 을 삭제해 전역 `:focus-visible`(2px solid) 로 되돌렸습니다.
hover 는 `:focus-visible` 을 켜지 않으므로 마우스 사용에는 영향이 없습니다.

서비스 전체에서 포커스 아웃라인을 지우는 규칙은 이제 `.field-input` 하나뿐이고,
그쪽은 브랜드 테두리 + 3px 링이라는 **대체 표시**가 있습니다(의도된 유지).

### 5-4. 키보드·콘솔 (실측)

- 캠페인 하위 탭 roving tabindex: 선택 탭 `tabindex=0`, 나머지 `-1`, `aria-selected` 일치
- ArrowRight → "링크 목록" → "링크 생성", ArrowLeft → 복귀. 양방향 동작 확인
- 전역 `:focus-visible => 2px solid var(--color-focus)` 규칙 존재 확인(CSSOM)
- 콘솔: 화면 전환·탭 이동·표 렌더 전 구간에서 error/warn **0건**

### 5-5. 겹침으로 보였던 3건은 오탐이었다

홈에서 겹침 3건이 잡혔으나 모두 `aria-hidden="true"` 인 결과 패널과의 겹침이었습니다.
`aria-hidden` 만으로는 포인터·탭 순서가 남으므로 실제로 확인했습니다.

- `visibility: hidden`, `pointer-events: none` 적용됨
- 입력칸 중앙 hit-test → 숨은 패널이 아니라 실제 `INPUT.field-input` 이 받음
- 숨은 패널의 버튼에 `focus()` 시도 → `document.activeElement` 로 이동하지 않음

가시성을 반영해 다시 세면 실제 겹침은 **0건**(320px 에서도 0건)입니다.
검출기가 `visibility` 를 보지 않은 것이 원인이었고, CSS 결함이 아닙니다.

## 6. 문구: 중복과 불필요한 아이브로우

### 6-1. 로그인 화면이 "로그인" 을 세 번 말했다

```
<title>로그인 - srrrg</title>
<p class="section-eyebrow">계정 로그인</p>   ← 삭제

```

문서 제목·아이브로우·h1 이 같은 정보를 반복했습니다. 아이브로우를 삭제했습니다.
설명("사용할 계정을 선택하세요. 비밀번호는 srrrg에 저장되지 않습니다.")은 남겼습니다 —
행동 지시와 보안 안심은 제목이 말하지 않는 정보입니다.

### 6-2. 초대 화면도 같은 형태

아이브로우 "프로젝트 초대" 아래 h1 이 두 갈래인데 양쪽 모두 "초대" 를 말합니다
("…에 초대받았습니다" / "사용할 수 없는 초대입니다"). 아이브로우를 삭제했습니다.

### 6-3. 결과: 죽은 CSS 2개 삭제

위 두 곳이 `.section-eyebrow` 의 유일한 사용처였습니다. `.section-kicker` 는 이미
템플릿·JS 어디에서도 쓰이지 않는 죽은 CSS 였습니다. 두 규칙과, `.section-kicker` 를
숨기던 `projects.css` 의 선택자 한 줄을 삭제했습니다.

### 6-4. 그대로 둔 문구와 이유

| 문구 | 판단 |
| --- | --- |
| `secret key`, `external_id`, `UTM`, `API key`, `code`, `OpenAPI JSON` | 영문 유지. 화면 밖(문서·API·CSV 헤더)에서 같은 이름을 쓰므로 번역하면 대응이 끊긴다 |

## 7. 320px 헤더: 캡처가 아니면 못 찾았을 결함

### 발견

측정값은 정상이었습니다 — `scrollWidth == clientWidth`, 가로 넘침 없음, 겹침 0.
그런데 **캡처를 보니 로그인 버튼 라벨이 "로그 / 인" 두 줄**로 쪼개져 있었습니다.

`.srrrg-header-login` 은 `padding: 0 var(--space-4)`(16px×2)이고 320px 에서 버튼 폭이 70px 로
눌려 내용 폭이 **38px**, "로그인" 은 약 **39px**. 1px 부족해서 줄바꿈했습니다.
줄바꿈은 넘침이 아니므로 `scrollWidth` 로는 잡히지 않습니다.

높이가 44px 로 나온 것은 `min-height: var(--touch-min)` 때문이며,
제가 처음 쓴 "높이÷줄높이" 추정은 이 값을 두 줄로 오판했습니다. 실제 판정은
`Range.getClientRects().length` 로 다시 했습니다.

### 수정

```css
.srrrg-header-link, .srrrg-header-login { white-space: nowrap; }

@media (max-width: 380px) {
	.srrrg-header-login { padding: 0 var(--space-3); }
}
```

`nowrap` 만 두면 워드마크 45 + 내비 240 = 285 에 gap 16 을 더해 301 > 300 으로 1px 넘칩니다.
가장 좁은 폭에서만 이 버튼의 좌우 여백을 12px 로 줄여 담았습니다.

### 검증

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 라벨 줄 수(`getClientRects().length`) | **2** | **1** |
| 버튼 폭 / 좌우 여백 | 70 / 16px | 63 / 12px |
| 필요 폭 vs 가용 | 301 vs 300 | **293 vs 300** |
| 워드마크 x / 내비 우측 여백 | — | 10 / 10 (대칭) |

캡처로 재확인했습니다.
