# srrrg 디자인 시스템 재설계

전체 서비스의 시각 언어를 다시 정의한 기록이다. 스타일 개선이 아니라
"모든 요소에 존재 이유가 있는가" 를 기준으로 토큰·컴포넌트·화면 위계를 다시 잡았다.

측정은 브라우저에서 직접 했다. 대비비는 WCAG 상대 휘도 공식으로 계산했고,
타입 스케일 이탈·터치 타깃·가로 오버플로·구조 표면 그림자는 렌더된 계산값을 세었다.

---

## 1. 굵기 다섯 종을 네 단계 역할로 정리

**기존 문제**
굵기 선언 73개 중 70개가 750 이상이었다. 분포는 800이 39개, 850이 12개, 900이 9개,
750이 7개, 880이 3개, 700이 2개, 500이 1개. 즉 다섯 종의 굵은 값이 섞여 있었고
본문을 뺀 거의 모든 요소가 굵었다.

**사용자에게 미치는 영향**
라벨·배지·버튼·내비게이션·표 머리가 모두 같은 무게라 화면에서 무엇이 중요한지
굵기로 판단할 수 없었다. 굵기가 위계 정보를 전달하지 못하는 상태였다.
또 750·850·880 은 가변 폰트가 아닌 시스템 폰트 스택에서 플랫폼마다 다르게
반올림되므로 Windows·macOS 에서 같은 화면이 다르게 보였다.

**선택한 변경안**
400 본문 / 500 데이터 값 / 600 라벨·버튼·표 머리 / 700 제목. 700 을 넘기지 않는다.
매핑은 800과 850을 600으로, 880과 900을 700으로, 750을 500으로 옮겼다.

**선택 근거**
각 단계에 역할을 하나씩 붙이면 굵기가 다시 신호가 된다.
700 상한은 시스템 폰트에서 플랫폼 간 렌더가 갈리는 구간을 피한다.
데이터 값에만 500을 준 것은, 값이 라벨보다 읽는 대상이지만 제목만큼
목소리를 낼 필요는 없기 때문이다.

**제외한 대안**
- 가변 폰트를 도입해 750·850을 정확히 렌더: 새 의존성이 생기고 한글 가변 폰트는 용량이 크다.
- 굵기를 두 단계(400/700)로 축소: 라벨과 제목을 같은 무게로 만들어 카드 안 위계가 사라진다.

**영향받는 화면과 파일** 전 화면. `base.css` 및 CSS 12개 파일.

**검증 결과** 숫자 굵기 선언 0개. 분포는 semibold 53 / bold 13 / medium 8 / normal 1.

## 2. 31종 글자 크기를 8단 스케일로

**기존 문제**
font-size 고유값이 31종이었다. 13px 30회, 12px 28회, 11px 15회, 14px 11회로
11~14px 구간에 84개 선언이 몰려 있었고, 제목용 `clamp()` 이 9종이었는데 전부 일회성이었다
(`clamp(36px,4.5vw,48px)`, `clamp(26px,3vw,32px)`, `clamp(20px,2.4vw,28px)` 등).

**사용자에게 미치는 영향**
비슷하지만 다른 크기(11 / 12 / 13px)가 인접해 있어 같은 위계인지 아닌지 알 수 없었다.
제목 크기가 화면마다 달라 같은 깊이의 화면이 서로 다른 층처럼 보였다.

**선택한 변경안**
12 / 13 / 14 / 15 / 17 / 20px 고정 6단 + `--text-2xl`(clamp 22~26) + `--text-3xl`(clamp 28~36).
11px 은 없앴다 — 한글 본문에서 11px 은 자소 판별이 어렵다.
유동 크기는 가장 큰 두 단계에만 남겼다.

**선택 근거**
UI 밀도가 높은 제품이라 배수가 큰 스케일은 맞지 않는다. 인접 단계 차이를 1~3px 로 두어
같은 위계는 같은 값을, 다른 위계는 분명히 다른 값을 갖게 했다.
본문 이하 크기를 고정한 것은, 유동 크기가 좁은 폭에서 라벨과 본문을 같은 크기로
수렴시켜 위계를 무너뜨렸기 때문이다.

**제외한 대안**
- 모듈러 스케일(1.25배): 14px 다음이 17.5px 로 표·배지에 쓸 중간값이 없어진다.
- rem 기반 전환: 기존 파일 전체가 px 이고, 혼용하면 계산이 두 갈래가 된다.

**영향받는 화면과 파일** 전 화면. `base.css` 및 CSS 12개 파일.

**검증 결과** 하드코딩 px·clamp font-size 0개. 렌더된 화면에서 스케일 이탈 크기 0종
(홈·워크스페이스·캠페인 3개 탭 전부).

## 3. 구조 표면에서 그림자를 걷어내고 실제 부유 레이어에만 남김

**기존 문제**
`--shadow-panel: 0 18px 50px rgba(15,23,42,0.08)` 이 `.surface-panel` 을 통해
템플릿 31곳에 적용됐다. 여기에 `.create-tool`·`.management-gate`·`.decision-panel` 이
각자 `0 14px 36px` 을 따로 갖고 있었고, `--shadow-tab` 은 선택 상태 표시에,
`.primary-button` 은 브랜드색 글로우(`0 8px 18px rgba(37,99,235,.18)`)를 갖고 있었다.

**사용자에게 미치는 영향**
모든 면이 떠 있으면 무엇이 실제로 떠 있는 레이어(팝오버·모달·드로어)인지 구분되지 않는다.
z축이 정보를 전달하지 못하고 화면 전체가 부유하는 인상만 남는다.
선택 상태를 그림자로 알리는 것도 의미가 어긋난다 — 그림자는 "떠 있음" 이고 선택은 "고름" 이다.

**선택한 변경안**
- `--shadow-panel: none`. 구조 표면은 `--color-border` 테두리로만 경계를 만든다.
  카드가 페이지 배경(`--color-canvas`)보다 밝아 1px 테두리로도 면이 분리된다.
- `--shadow-raised` (2겹, 부드러움): 프로젝트 전환 팝오버, 계정 팝오버, UTM 팝오버, 생성 디스클로저.
- `--shadow-overlay`: 모달, 모바일 드로어.
- 선택 상태는 전부 채운 면(브랜드색 배경 + 흰 글자)으로 교체.
- primary 버튼 글로우 제거, hover `translateY(-1px)` 제거.

**선택 근거**
그림자를 z축 정보로 되돌린다. 떠 있는 것만 그림자를 가지면 사용자는 그림자를 보고
"이건 위에 뜬 임시 레이어" 라고 읽을 수 있다.
장식용 hover 리프트는 상태를 알리지 않으면서 클릭 지점을 미세하게 움직인다.

**제외한 대안**
- 그림자를 전부 없애기: 팝오버가 아래 콘텐츠와 붙어 보여 부유 여부를 알 수 없다.
- 그림자를 더 약하게만 조정: 31개 면이 여전히 떠 있어 문제의 성격이 그대로 남는다.

**영향받는 화면과 파일** 전 화면. `base.css`, `components.css`, `layout.css`,
`home.css`, `decision.css`, `projects.css`, `campaigns.css`, `management.css`.

**검증 결과** 렌더된 화면에서 그림자를 가진 `.surface-panel` 0개
(홈·워크스페이스·캠페인 3개 탭). 팝오버 4곳은 `--shadow-raised` 유지.

## 4. 포커스 링을 불투명하게

**기존 문제**
`--color-focus: rgba(37,99,235,0.18)` 로 3px 아웃라인을 그렸다.
흰 배경에서 실효 색이 약 #d6e0f8 이고 대비는 약 1.3:1 이었다.
`.oauth-button` 은 `rgba(49,130,206,0.2)` 로 hover 와 focus 가 같은 링을 공유했다.
`.field-input:focus` 도 같은 반투명 아웃라인을 썼다.

**사용자에게 미치는 영향**
키보드만으로 조작할 때 지금 어디에 있는지 알 수 없었다. WCAG 2.4.11(비텍스트 대비 3:1) 미달.

**선택한 변경안**
`:focus-visible` 을 불투명 2px 브랜드색 링 + 2px 오프셋으로 바꿨다.
짙은 면(primary·danger 버튼) 위에서는 링을 흰색으로 뒤집고 오프셋을 안쪽으로 준다.
입력 필드는 아웃라인 대신 테두리를 브랜드색으로 바꾸고 3px 브랜드 소프트 링을 더한다 —
필드는 경계가 이미 있으므로 그 경계를 강조하는 편이 위치를 더 정확히 알린다.
`.oauth-button` 의 hover 와 focus 를 분리해 hover 는 면 색으로만 알린다.

**선택 근거**
포커스는 "지금 여기" 를 알리는 유일한 신호라 배경과 무관하게 보여야 한다.
색이 짙은 면에서 링을 뒤집는 것은 브랜드색 버튼 위에서 브랜드색 링이 사라지는 문제를 막는다.

**제외한 대안**
- 두께만 키우기(3px 유지): 투명도가 원인이라 두꺼워도 대비는 그대로다.
- `box-shadow` 링으로 통일: `overflow: hidden` 컨테이너 안에서 잘린다.

**영향받는 화면과 파일** 전 화면. `base.css`, `components.css`.

**검증 결과** `:focus-visible` 이 `outline: 2px solid var(--color-focus)` 로 해석되고
적용 시 `rgb(31,87,214)` solid. 반투명 링 잔존 0개.

## 5. 보조 버튼을 중립으로 내려 주 행동과 분리

**기존 문제**
`.secondary-button` 이 브랜드 소프트 배경 + 브랜드 테두리 + 브랜드 글자였다.
`.copy-button` 도 브랜드색 pill 이었다. `.primary-button` 은 브랜드 면 + 글로우.
결과적으로 한 줄에 파란 요소가 둘 이상 놓여 무엇이 주 행동인지 색으로 구분되지 않았다.

**사용자에게 미치는 영향**
"다음에 무엇을 할 수 있는가" 를 색으로 읽을 수 없었다. 특히 링크 생성 결과 패널처럼
주 행동(복사)과 보조 행동(관리 화면 열기, 새 링크)이 나란히 놓인 화면에서 시선이 갈렸다.

**선택한 변경안**
브랜드색은 네 가지 역할에만 쓴다 — 주 행동, 링크, 포커스, 선택 상태.
`.secondary-button` 은 흰 면 + 중립 테두리 + 본문색.
`.copy-button` 은 중립 버튼으로 내리고 고정 폭(64px)을 없앴다.
`.danger-button` 은 면을 채우지 않고 색과 테두리로만 경고한다 —
이 버튼은 확인 대화상자를 여는 단계이고, 실제 실행은 대화상자 안에서 일어난다.

**선택 근거**
색 대비가 위계를 만든다. 화면에 파란 면이 하나면 그것이 주 행동이라는 규칙이 성립한다.
복사 버튼 고정 폭을 없앤 것은 "복사됨" 으로 라벨이 바뀔 때 글자가 잘렸기 때문이다.

**제외한 대안**
- secondary 를 회색 면으로: 비활성 버튼과 구분되지 않는다.
- danger 를 채운 빨강으로: 삭제 확인 전 단계인데 실행 버튼처럼 보인다.

**영향받는 화면과 파일** 전 화면. `components.css`, `layout.css`.

**검증 결과** 렌더된 화면에서 보이는 `.primary-button` 개수 — 홈 1, 워크스페이스 1,
캠페인 개요 1, 링크 목록 0, 캠페인 설정 2.
설정 탭의 2개는 독립된 폼(캠페인 정보 저장 / 기본 목적지 저장)의 각 제출 버튼이라
의도한 결과다. 폼마다 자기 제출을 primary 로 갖는 것이 표준이고,
"화면당 하나" 는 단일 지배 행동이 있는 화면의 규칙이다.

## 6. 지표 6개를 하나의 면으로 묶고 성과 지표만 강조

**기존 문제**
전체 진입 / 전체 이동 / 사람 진입 / 사람 이동 / 미이동 / 봇 진입 6개가
각각 테두리와 반경을 가진 카드로 떨어져 있었고, 값 크기와 굵기가 모두 같았다.

**사용자에게 미치는 영향**
이 값들은 "전체 대 사람", "진입 대 이동" 으로 **비교해서** 읽는 값인데
카드 6개의 테두리가 쌍의 관계를 끊었다. 또 실제 성과(사람 이동)와
진단 수치(봇 진입)가 같은 무게라 무엇을 먼저 봐야 하는지 알 수 없었다.

**선택한 변경안**
하나의 테두리 안에 `gap: 1px` + 배경색을 비쳐 구분선을 만들었다.
사람 진입·사람 이동만 값을 한 단계 키우고, 미이동·봇 진입은 색과 굵기를 낮췄다.

**선택 근거**
1px 간격 기법은 열 수가 바뀌는 반응형 구간(3열 → 2열 → 1열)에서
`nth-child` 계산 없이 격자가 유지된다. 강조는 값의 크기로만 주고 라벨은 건드리지 않아
"어떤 지표인지" 는 그대로 읽히게 했다.

**제외한 대안**
- 성과 지표 2개만 위에 크게 두고 나머지를 접기: 진단 수치도 매일 보는 값이다.
- DOM 순서 재배치: 전체/사람 쌍의 대응이 깨진다.

**영향받는 화면과 파일** 프로젝트 통계 탭, 캠페인 개요 탭, `/manage` 통계 탭.
`management.css`.

**검증 결과** 모바일 강제 시 1열로 접히고 구분선 유지, 가로 오버플로 없음.

## 7. 홈: 입력창에 닿기 전 같은 메시지 네 겹을 한 겹으로

**기존 문제**
사용자가 URL 입력창에 도달하기까지 읽어야 하는 문구가 네 겹이었다 —
헤더 태그라인("빠르고 안전한, 무료 단축 URL") + 눈썹 배지("srrrg.link") +
h1("긴 링크를 짧고 안전하게") + 설명 두 문장.
아래에는 기능 3개 섹션, 관리 화면 섹션(제목+설명+버튼), API 링크 줄이 이어졌다.

**사용자에게 미치는 영향**
이 화면의 목적은 "URL 하나 붙여넣고 단축 링크 받기" 하나다.
같은 말을 네 번 읽는 동안 실제 도구(입력창)는 시선 밖에 있었다.
관리 화면 섹션은 제목+설명+버튼으로 약 120px 을 차지했는데,
헤더에 같은 링크가 이미 있어 세 번째 입구였다.

**선택한 변경안**
- 눈썹 배지 삭제. 헤더 워드마크가 이미 말하는 도메인을 되풀이할 뿐이다.
- 설명은 발급되는 것(링크 + secret key)만 남기고 위협 차단 문장은 아래 기능 목록에 맡겼다.
- 관리 화면 섹션을 한 줄로 축소("이미 만든 링크가 있나요? / secret key로 …" + 텍스트 링크).
  카드도 버튼도 쓰지 않는다 — 카드는 새 링크 만들기와 같은 무게를 주고 버튼은 주 행동과 경쟁한다.
- 기능 3개의 문구에서 판정 한계 설명("오탐이나 미탐") 을 뺐다.

**선택 근거**
빈도가 위계를 정한다. 새 링크 만들기가 압도적으로 잦고, 재진입은 그다음이며,
API 는 대상이 다르다. 판정 한계는 실제로 차단이 일어난 화면에서
Safe Browsing 고지와 함께 읽어야 의미가 있다.

**제외한 대안**
- 관리 화면 진입을 아예 제거하고 헤더에만 남기기: 비회원에게는 이 줄이
  발급받은 secret key 로 돌아올 수 있는 유일하게 설명이 붙은 경로다.
- 기능 3개 섹션 제거: 단축 URL 서비스에서 "무엇을 믿고 쓰는가" 는 실제 판단 근거다.

**영향받는 화면과 파일** 비회원 홈.
`fragments/home/product-intro.html`, `trust-features.html`, `manage-entry.html`, `home.css`.

**검증 결과** 문서 높이 1024px → 952px. 대비 실패 0, 스케일 이탈 0,
보이는 primary 버튼 1개, 가로 오버플로 없음.

## 8. 프로젝트 요약: 주소가 보인다는 이유로 붙어 있던 복사 버튼 제거

**기존 문제**
"프로젝트 개요" 카드에 링크·캠페인 수가 큰 숫자 카드 2개로 있었고,
그 아래 발급 도메인과 복사 버튼이 한 줄로 있었다.
카드 설명에는 "캠페인과 단축링크는 왼쪽 콘텐츠 목록에서 바로 열 수 있습니다" 가 적혀 있었다.

**사용자에게 미치는 영향**
도메인 복사 버튼은 주소가 표시됐다는 이유로 붙어 있었지만,
origin 만으로는 아무 곳에도 쓸 수 없다 — 링크는 코드가 붙어야 주소가 되고,
실제 복사는 생성 결과 패널과 링크 목록의 행별 복사 버튼이 담당한다.
즉 누를 이유가 없는 버튼이 상태 표시 줄에 행동처럼 놓여 있었다.
"왼쪽 목록에서 열 수 있습니다" 안내도 레일이 화면에 보이는 상태에서
조작 방법을 문장으로 설명하는 중복이었다.

**선택한 변경안**
요약을 상태 전용 한 줄로 바꿨다 — 단일링크 수 / 캠페인 수 / 발급 도메인.
복사 버튼과 안내 문장을 지웠고, 숫자 크기를 `--text-lg` 로 낮췄다.
도메인은 등폭 글꼴로 두고 좁아질 때 먼저 줄바꿈되게 했다.

**선택 근거**
이 줄의 역할은 상태 확인이다. 다음 행동(링크·캠페인 만들기, 항목 열기)은 전부
왼쪽 레일에 있으므로 여기에 버튼을 두면 같은 행동의 두 번째 입구가 된다.
숫자를 낮춘 것은 통계 탭의 성과 지표와 경쟁하지 않게 하려는 것이다 —
여기 숫자는 규모 파악용이고 판단에 쓰는 수치는 통계 탭에 있다.

**제외한 대안**
- 복사 버튼을 유지하되 약하게: 누를 이유가 없다는 사실은 변하지 않는다.
- 도메인 전체를 제거: "새 링크가 어느 주소로 발급되는가" 는 서브도메인을
  선점한 팀에게 실제로 확인이 필요한 값이다.

**영향받는 화면과 파일** 프로젝트 워크스페이스. `templates/projects.html`,
`static/js/srrrg-projects.js`(핸들러 제거), `projects.css`.

**검증 결과** `#copy-project-domain` 부재, 요약 3항목 렌더 확인,
콘솔 오류 0, 문서 높이 2664px → 2203px.

## 9. 콘텐츠 텍스트를 placeholder 색에서 분리

**기존 문제**
`--color-text-placeholder` 를 `.help-text`, 레일 라벨("프로젝트 관리", "콘텐츠"),
레일 항목의 날짜 `<small>`, 빈 상태 문구에 쓰고 있었다.
흰 배경에서 대비 3.02:1 로 4.5:1 에 미달했다.

**사용자에게 미치는 영향**
도움말과 목록의 부가 정보가 읽기 어려웠다. 특히 도움말은
"이 필드에 무엇을 넣어야 하는가" 를 알리는 콘텐츠라 흐리면 기능을 잃는다.

**선택한 변경안**
placeholder 색은 실제 `::placeholder` 와 비활성 컨트롤에만 남기고,
콘텐츠 텍스트는 `--color-text-subtle`(#5f6b80, 약 5.4:1)로 올렸다.
비활성 버튼 라벨도 placeholder 색(2.72:1)에서 subtle 로 올렸다 —
무엇을 할 수 있는 버튼인지 읽혀야 활성 조건을 짐작할 수 있다.

**선택 근거**
placeholder 는 입력 예시라 사라져도 정보 손실이 없지만, 도움말·라벨·날짜는 콘텐츠다.
색 하나를 두 역할에 쓰면 한쪽이 반드시 기준에 못 미친다.

**영향받는 화면과 파일** 전 화면. `components.css`, `projects.css`.

**검증 결과** 렌더된 4개 화면에서 대비 실패 0개
(수정 전 워크스페이스에서 3.02:1 4건).

## 10. 그 밖의 정돈

**색을 토큰으로** 토큰 밖 hex 가 18곳 있었다 — 샘플 배지의 `#fff8d8`,
차트 축의 `#7b8798`, 콘솔 패널의 `#f8fafc`, 레일 템플릿 글리프의 보라색 `#7c3aed` 등.
전부 토큰으로 옮겼다. 특히 레일 글리프 네 종 중 template 만 보라색이라
팔레트 밖에 있었는데, 종류는 글리프 문자가 구분하므로
"캠페인=브랜드, 나머지=중립" 두 갈래로 줄였다. 남은 hex 는 브랜드 면 위의 흰 글자뿐이다.

**`/manage` 기간 필터** 이 블록만 한 줄로 압축된 채 rem 값과 hex 를 직접 써서
(`min-height:2.4rem; border-radius:.5rem; background:#fff`) 나머지 화면과 어긋나 있었다.
통계 화면의 같은 필터와 동일하게 `.field`/`.field-label`/`.field-input` 으로 교체했다.

**컨트롤 높이** 44~48px 이던 기본 컨트롤을 40px 로 낮추고 터치 타깃은 여백으로 확보했다.
이전에는 컨트롤 자체가 커서 폼이 실제 정보량보다 무거워 보였다.

**배지** pill + 테두리라 표·목록 안에서 버튼으로 오인됐다.
사각에 가깝게 두고 테두리를 없애고, 상태색 배지는 좌측 3px 마커로 종류를 알린다
(색만으로 구분하지 않기 위해).

**눈썹 라벨** 브랜드색 pill 이라 배지·버튼과 구분되지 않았다.
색 면을 버리고 대문자 자간과 색으로만 구분한다.

**삭제 영역** 면 전체가 붉어서 화면 아래쪽이 항상 경고처럼 보였고
실제로 위험한 순간(확인 대화상자)과 구분되지 않았다.
중립 면에 좌측 마커만 남겨 "여기부터 성격이 다르다" 만 알린다.

**행 선택 체크박스** 17px 에서 20px 로 올렸다. 24px 정사각형까지 키우지 않은 것은
표 밀도를 유지해야 하기 때문이고, 주변 여백이 충분해
WCAG 2.5.8 의 간격 예외(24px 원이 다른 타깃과 겹치지 않음)를 만족한다.

**모션** 장식용 전환을 지웠다. 남긴 것은 상태 전환을 이해시키는 것뿐이다 —
버튼·칩의 면 색 전환(120ms), 드로어 슬라이드(180ms), 생성 결과 패널 교체.
`prefers-reduced-motion` 에서 전부 사실상 0으로 줄인다.

## 보존한 것과 이유

**왼쪽 레일의 구조와 역할** 항목 구성·순서·동작을 그대로 뒀다.
글리프 색을 팔레트에 맞추고 라벨 대비를 올리고 글리프 크기를 28px → 26px 로
조정한 것이 전부다. 요청 범위이자, 이 레일은 이미 워크스페이스의
탐색 축으로 기능하고 있어 구조를 바꿀 근거가 없었다.

**프로젝트 이름 옆 드롭다운 전환 구조** `<details>` + 팝오버 방식과
항목 렌더링을 유지했다. 팝오버에 `--shadow-raised` 를 주어
부유 레이어임을 분명히 한 것과 옵션 글자 색·굵기를 스케일에 맞춘 것만 바꿨다.

**캠페인 상세의 4개 탭 구조** 개요/링크 목록/링크 생성/설정 구분이
작업 단위와 일치해 그대로 뒀다. `console-tabs` 컴포넌트를 프로젝트 화면에도
재사용해 두 화면의 조작 방식을 통일했다.

**기존 접근성 구현** roving tabindex, `inert` 기반 드로어 격리,
결과 패널 포커스 이동, `sr-only` 표 헤더, 차트 `<title>/<desc>` 를 모두 유지했다.
새로 추가한 프로젝트 탭에도 같은 roving tabindex 방식을 적용했다.

## 11. 시각 검증 결과 (실제 렌더링 캡처 기준)

앞선 재설계는 수치 계측만으로 검증했고 "시각 확인 불가" 를 한계로 남겼다.
이후 스크린샷 캡처가 가능해져 실제 렌더링을 데스크톱·태블릿·모바일에서 확인했다.
아래는 **캡처로 발견해 고친 것**, **캡처 방식 문제로 판별한 것**, **보고 유지한 것** 세 갈래다.

### 캡처 도구별 신뢰도 (먼저 판별한 것)

| 도구 | 결과 | 판단 |
|---|---|---|
| Chrome 데스크톱 캡처 | 1064×947~1046, 콘텐츠가 프레임을 채우고 요소 좌표가 `getBoundingClientRect` 와 일치 | **광학 판단에 신뢰 가능** |
| Chrome `resize_window` | `Invalid value for bounds. Bounds must be at least 50% within visible screen space` | 화면 밖으로 나가 실패. 좁은 폭 캡처 불가 |
| 인앱 브라우저 viewport 프리셋 | 768×1024 / 375×812 로 잡히고 `innerWidth` 도 일치하지만, 캡처 이미지의 요소 위치가 실측과 어긋남(모바일에서 `.service-facts` 실측 605px, 캡처상 약 310px) | **레이아웃 유무 확인에는 쓸 수 있으나 광학 판단에는 부적합.** 좁은 폭은 강제 CSSOM 규칙 + 실측으로 검증 |

특히 두 가지를 "실제 CSS 문제가 아님" 으로 판별했다.

- **워크스페이스 캡처 하단의 빈 띠** — 캡처 이미지가 1046px 인데 실제 viewport 는 1011px,
  문서 높이는 2157px 로 정상 스크롤된다. 캡처 캔버스가 합성 영역보다 큰 것이지 레이아웃 공백이 아니다.
- **모바일 캡처에서 관리 진입·API·푸터가 안 보이던 것** — 실측으로 전부 존재하고
  푸터가 1087~1168px 에 있다(문서 1168px). 인앱 캡처의 축척 불일치였다.

- **`Frame with ID 0 is showing error page`** 는 캡처 문제가 아니라 devtools 재시작 중
  실제 내비게이션 실패였다. 앱이 실제 콘텐츠를 연속 12회 서빙할 때까지 기다린 뒤 재시도해 해결했다.

### 캡처로 발견해 고친 것 (5건)

**11-1. 생성 패널 안의 57px 빈 공간**

입력 상태와 결과 상태가 같은 grid cell 을 공유해 행 높이가 큰 쪽(결과 401px)으로 고정됐다.
입력 상태(368px)에서 패널 아래에 57px 가 비어 패널이 고장난 것처럼 보였다.
숨은 상태를 `position: absolute` 로 빼 높이가 보이는 상태를 따라가게 했다.
높이 변화는 사용자가 만들기를 눌러 내용이 실제 바뀌는 순간에만 일어나므로
의미 없는 점프가 아니라 상태 변경 신호다.

- 실측 빈 공간 **57px → 25px**(패널 하단 패딩), 패널 높이 450px → 365px.
- 회귀 확인: 결과 상태 렌더 정상.
- 파일 `home.css`

**11-2. 만료 "없음" 인데 자리를 차지하던 비활성 "-" 행**

캡처에서 비활성 회색 바 두 개(만료 표시, 비활성 제출 버튼)가 연달아 놓여
어느 것이 무엇인지 읽히지 않았다.

처음에는 "쓸모 없는 UI" 로 판단했지만 옵션별로 값을 확인해 보니 판단이 바뀌었다 —
`1시간` 을 고르면 `2026-08-12T17:51` 처럼 **선택이 정확히 몇 시 몇 분인지 알려주는 읽기 전용 표시**였다.
알릴 내용이 없는 것은 "없음" 하나뿐이었다. 그래서 전체를 지우지 않고 "없음" 일 때만 감췄다.

같은 기능인데 워크스페이스는 이미 `hidden` 으로 감추고 홈은 감추지 않아 화면 간 동작도 어긋나 있었다.
초기화 경로(`resetExpiresAt`, `updateExpiresAtOption`)가 페이지 로드 시 호출되지 않아
템플릿 기본값에 `hidden` 을 주어 초기 DOM 상태가 초기 선택 상태와 일치하게 했다.

- 회귀 확인: `직접 입력` → 필드 노출·활성·프리필·**포커스 이동** 정상,
  `1시간` → 노출·비활성·시각 표시 정상, `없음` → 다시 감춤. 콘솔 오류 0.
- 파일 `fragments/home/create-panel.html`, `srrrg-home.js`

**11-3. 통계 제목과 기간 표시가 35px 벌어짐**

캡처에서 "내 프로젝트 통계" 와 기간 줄 사이가 과하게 떠 있었다.
원인은 `p` 기본 마진 1em(15px)이 컨테이너 `gap`(20px)과 더해진 것이다.
`base.css` 에서 `p { margin: 0 }` 으로 전역 정리했다 — 문단 간격은 레이아웃이 정한다는 원칙과 같다.
기간 표시는 본문 크기·본문 색이라 데이터 문장처럼 읽혀서 메타데이터로 낮췄다.

- 실측 간격 **35px → 8px**, 기간 표시 15px/본문색 → **13px/`--color-text-subtle`**.
- 부수 효과: 전역 `p { word-break: keep-all }` 로 로그인 설명의
  "…저장되지 / 않습니다." 고아 줄바꿈이 "…srrrg에 / 저장되지 않습니다." 로 개선됐다.
- 파일 `base.css`, `statistics.css`

**11-4. 필터 "적용" 이 지표보다 시각적으로 강함**

브랜드 면을 채운 primary 라 통계 패널에서 가장 눈에 띄는 요소가 데이터가 아니라 필터 버튼이었다.
이 화면의 목적은 데이터를 읽는 것이고 기간 변경은 그 수단이다.
`/manage` 의 같은 버튼은 이미 secondary 라 화면 간에도 어긋나 있었다.

- `primary-button` → `secondary-button`. 실측 배경 `rgb(31,87,214)` → `rgb(255,255,255)`.
- 파일 `statistics.html`

**11-5. 기간 칩 그룹이 같은 행의 날짜 입력보다 8px 높음**

`padding 3px + 버튼 40px + 테두리 2px = 48px` 로 옆의 40px 입력과 높이가 어긋났다.
아래쪽 정렬이라 즉시 틀려 보이지는 않지만 컨트롤 높이가 제각각으로 읽힌다.

- 컨테이너 padding 2px + 버튼 34px 로 **40px** 로 맞춰 입력과 동일. 하단 정렬 유지.
- 파일 `management.css`

**11-6. 로그인 카드가 상단 1/3 에 뜨고 아래 약 300px 가 빔**

`.login-shell` 에 높이가 없어 `place-items: center` 의 세로 중앙이 아무 일도 하지 않았다.
카드 하나뿐인 인증 화면에서 미완성처럼 보였다. `flex: 1` 로 남는 높이를 받게 했다.

- 카드가 사용 가능 영역의 세로 중앙에 놓임(캡처 확인).
- 파일 `components.css`

### 보고 유지한 것

**카드 경계(그림자 제거)** — 직전 작업의 가장 큰 우려였다. 캡처로 확인한 결과
`#f6f7f9` 캔버스 위 흰 카드 + `#e3e7ec` 테두리로 면이 **분명히 구분된다**.
홈 생성 패널, 로그인 카드, 워크스페이스 요약·탭 패널 모두 경계가 읽힌다.
그림자를 되살릴 근거를 찾지 못했으므로 유지한다.

**본문 15px / 컨트롤 40px 밀도** — 두 번째 우려였다. 캡처에서 홈 폼(라벨 13px + 입력 40px)과
워크스페이스 지표가 답답하지 않고, 오히려 이전 44~48px 컨트롤보다 폼이 가벼워 보인다.
한글 13px 라벨도 판별에 문제가 없다. 유지한다.

**지표 강조** — 사람 진입·이동(더 큰 값)과 미이동·봇(흐린 값)의 차이가
캡처에서 의도대로 구분된다. 한 면 + 1px 구분선이 6개 카드보다 쌍을 비교하기 쉽다. 유지한다.

**선택 상태(채운 브랜드 면)** — 만료 "없음" 칩과 기간 "30일" 칩이 캡처에서
즉시 선택 상태로 읽힌다. 그림자 대신 면을 쓴 판단이 맞았다. 유지한다.

**태블릿 만료 칩 3×2 줄바꿈** — 768px 에서 6칩이 3열 2행으로 접힌다.
6열을 유지하면 칩 폭이 약 40px 로 라벨이 잘린다. 유지한다.

**모바일 만료 디스클로저** — 375px 에서 칩 6개가 "만료 설정 / 없음" 한 줄로 접힌다.
기존 반응형 설계가 이미 옳아 건드리지 않았다.

**눈썹 라벨의 `text-transform: uppercase`** — 한글에는 시각 효과가 없다(로그인 "계정 로그인" 확인).
영문 눈썹에는 작동하고 자간·색 구분은 한글에도 적용되므로 해가 없어 남긴다.

**통계 제목의 프로젝트명 중복** — h1 "내 프로젝트" 아래 h3 "내 프로젝트 통계" 로 이름이 반복된다.
같은 조각이 캠페인 화면에서는 캠페인명을 보여줘 유용하므로,
조각을 맥락별로 분기시키는 비용이 이득보다 크다고 판단해 남긴다.

**짧은 페이지의 푸터 아래 여백** — body 가 `min-height: 100vh` 이고 푸터가 `margin-top: auto` 라
콘텐츠가 짧으면 푸터가 viewport 하단에 붙고 그 위가 빈다. 의도된 동작이다.

### 남은 한계

**좁은 폭 광학 검증** — Chrome 창 리사이즈가 화면 경계 제약으로 실패하고
인앱 캡처는 축척이 어긋나, 태블릿·모바일은 **레이아웃 유무와 실측값으로만** 확인했다.
접힘·오버플로·컨트롤 높이는 검증됐지만 좁은 폭에서의 광학 균형은 사람 눈이 필요하다.

**워크스페이스 좁은 폭 캡처** — 인앱 브라우저에 세션이 없어 로그인 화면 이후를
좁은 폭으로 캡처할 수 없었다. 강제 CSSOM 규칙 + 실측으로 대체했다.

**조회 전용(VIEWER)** — 접근 가능한 프로젝트가 모두 OWNER 라 여전히 미확인.
