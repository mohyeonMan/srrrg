# UI/UX 결정 기록

UI/UX 개선 과정에서 선택지가 생겼을 때 무엇을 왜 골랐는지 누적 기록한다.
새 결정은 아래에 계속 덧붙인다.

## 1. 캠페인 탭 키보드 이동 (재수색 #2)

**문제와 맥락**
`campaigns.html` 의 캠페인 상세 탭 4개는 `role="tablist"` / `role="tab"` 을 쓰지만 방향키 핸들러와
roving tabindex 가 없었다. 탭 4개가 모두 Tab 순서에 남고 좌우 방향키는 동작하지 않아
WAI-ARIA Authoring Practices 의 Tabs 패턴을 벗어난다.
같은 `console-tab` 클래스를 쓰는 `management.html` 탭은 이미 올바르게 구현돼 있었다.

**채택안**
`srrrg-management.js` 의 탭 처리 방식을 그대로 옮긴다. 선택된 탭만 `tabIndex = 0` 이고 나머지는 `-1`,
`ArrowLeft` / `ArrowRight` 로 이동하며 이동 시 포커스도 함께 옮긴다. 탭 4개라 순환 인덱스로 일반화했다.

**선택 근거**
정답 구현이 이미 저장소 안에 있어 새 패턴을 만들 이유가 없다. 동일 컴포넌트가 화면에 따라
다르게 동작하던 불일치도 함께 사라진다.

**제외한 대안**
- 라이브러리 도입: 새 의존성 금지 원칙에 어긋나고 8줄로 해결되는 문제다.
- `Home` / `End` 키까지 추가: APG 권장이지만 `management.js` 에 없어 두 화면이 다시 갈라진다.
  두 화면을 함께 올릴 때 별도로 다루는 편이 낫다.

**영향 파일** `static/js/srrrg-campaigns.js`

**검증** 데스크톱에서 `개요 → 링크 목록 → 링크 생성 → 설정` 을 방향키로 순회, `aria-selected` 와
`tabIndex` 가 함께 갱신되고 순환도 동작함을 확인.

## 2. 제출 피드백과 중복 제출 방지 (재수색 #4)

**문제와 맥락**
submit 핸들러 13개 중 9개가 처리 중 표시 없이 즉시 요청만 보냈다. 특히 프로젝트 생성과
템플릿 생성은 버튼 비활성화도 없어 더블클릭하면 실제로 2개가 만들어졌다.

**채택안**
`SrrrgCommon.submitting(button, pendingLabel, run)` 헬퍼를 추가한다. 버튼을 비활성화하고 라벨을
처리 중 문구로 바꾼 뒤 `finally` 에서 되돌리며, `dataset.pending` 으로 재진입을 막는다.
대상 핸들러는 `event.submitter` 를 넘겨 호출하고 기존 `form-message` 에 진행 문구를 함께 넣는다.

**선택 근거**
이미 `srrrg-common.js` 가 공용 모듈로 존재해 새 파일이나 의존성이 필요 없다. 버튼 잠금과
라벨 복구가 한곳에 모여 화면마다 다르게 구현될 여지가 없다. `finally` 복구라 실패 경로에서도
버튼이 잠긴 채 남지 않는다.

**제외한 대안**
- 각 핸들러에서 개별 처리: 기존에 로딩 표시가 있던 4곳이 이미 서로 다른 방식이었고,
  9곳을 각각 쓰면 불일치가 더 커진다.
- 전역 폼 submit 가로채기: 검증 실패로 요청을 보내지 않는 경우까지 잠기고, 어떤 버튼이
  제출 주체인지 판별이 불안정하다.
- 서버측 멱등키: 이번 UI/UX 범위를 벗어난다. CSV 업로드에만 이미 존재한다.

**영향 파일** `static/js/srrrg-common.js`, `srrrg-campaigns.js`, `srrrg-projects.js`,
`srrrg-project-settings.js`, `srrrg-project-utm-templates.js`

**검증** 프로젝트 생성 버튼을 연속 클릭해도 POST 가 1회만 나가고, 처리 중 라벨이 바뀌고
완료 후 원래 라벨로 복구됨을 확인.

## 3. 확인 대화상자를 네이티브 confirm 에서 <dialog> 로 (재수색 #5)

**문제와 맥락**
삭제·반납 등 되돌리기 어려운 동작 7건이 브라우저 `confirm()` 을 썼다. 디자인 시스템 밖이고,
브라우저가 "추가 대화상자 표시 안 함" 으로 억제할 수 있으며, 문구에 `410 Gone` 같은
HTTP 용어가 그대로 노출됐다.

**채택안**
`projects.html` 에 공용 `<dialog id="confirm-dialog">` 하나를 두고 `SrrrgCommon.confirmAction()` 이
제목·본문·버튼 라벨을 채워 `showModal()` 로 띄운다. Promise 로 결과를 돌려준다.
기본 포커스는 취소에 두고, 실행 버튼은 위험도에 따라 `danger-button` / `primary-button` 을 쓴다.
개발자 용어는 사용자 관점 문구로 바꿨다. 예) `410 Gone 을 반환합니다`
→ `목적지가 사라져 이동하지 않습니다`.

**선택 근거**
이미 `create-project-dialog` 가 네이티브 `<dialog>` + `showModal()` 을 쓰고 있어 포커스 트랩과
Esc 닫기를 공짜로 얻는다. `.project-create-dialog` / `.project-dialog-heading` 스타일도 재사용된다.
대화상자 마크업을 하나만 두어 7곳이 같은 모양을 갖는다.

**제외한 대안**
- 화면마다 전용 대화상자: 마크업 7배, 스타일 불일치 위험.
- 커스텀 오버레이 div: 포커스 트랩과 Esc 처리를 직접 구현해야 하고 접근성이 후퇴한다.
- confirm 유지하고 문구만 수정: 억제 가능성과 스타일 불일치가 남는다.

**트레이드오프**
대화상자가 없는 화면에서 `confirmAction()` 은 `true` 를 반환해 동작을 막지 않는다.
현재 confirm 사용처는 모두 `projects.html` 안에 임베드되므로 문제가 없지만, 조각을 다른
페이지에서 쓰게 되면 그 페이지에도 대화상자를 넣어야 한다. 그 전제를 주석으로 남겼다.

**영향 파일** `templates/projects.html`, `static/js/srrrg-common.js`, `srrrg-campaigns.js`,
`srrrg-project-settings.js`, `srrrg-project-utm-templates.js`, `static/css/srrrg/projects.css`

**구현 중 바로잡은 두 가지**
- 처음에는 `dialog` 의 `close` 이벤트로 결과를 확정했는데, 검증 환경에서 이 이벤트가 아예
  발생하지 않아 실행 버튼을 눌러도 Promise 가 영원히 대기했다. `dlg.close('accept')` 를
  직접 호출해도 이벤트가 없었다. 이벤트 의존을 버리고 열려 있는 대화상자의 resolver 를
  모듈 변수로 들고 있다가 버튼 클릭과 Esc 키에서 직접 확정하도록 바꿨다.
- 삭제 핸들러에서 `event.currentTarget` 을 `await confirmAction()` 이후에 사용했다.
  `currentTarget` 은 이벤트 전파가 끝나면 null 이 되므로 버튼을 미리 지역 변수로 잡아야 한다.

**영향 파일** `templates/projects.html`, `static/js/srrrg-common.js`, `srrrg-campaigns.js`,
`srrrg-project-settings.js`, `srrrg-project-utm-templates.js`, `static/css/srrrg/projects.css`

**검증** 수락 `true`, 취소 `false`, Esc `false` 로 각각 확정됨을 확인.
임시 캠페인을 만들어 실제 삭제까지 수행 → 대화상자 → 수락 → DELETE → 프로젝트로 복귀 →
목록에서 사라짐. 필드 삭제 대화상자도 확인. 네이티브 `confirm(` 잔존 0건, 콘솔 오류 0건.

## 4. CTA 위계 통일 (재수색 #6)

**문제와 맥락**
같은 레일에서 진입하는 형제 화면인데 `프로젝트 만들기` / `단축 URL 만들기` 는 primary,
`캠페인 만들기` 는 secondary 였다. `project-utm-templates`, `project-settings`,
`project-members` 는 primary 버튼이 아예 0개여서 각 화면의 주 동작이 드러나지 않았다.

**채택안**
"화면 또는 카드마다 주 동작 하나를 primary 로 둔다" 는 규칙을 적용했다.
캠페인 만들기, 템플릿 만들기, 필드 추가, 초대 보내기, 캠페인 정보 저장, 기본 목적지 저장,
CSV 업로드, 이름 저장, 선점하기, 프로젝트로 편입을 primary 로 올렸다.
보조 동작(더 보기, CSV 다운로드, 새 템플릿 열기)과 파괴적 동작(삭제)은 그대로 두었다.

**선택 근거**
핵심 사용자인 캠페인 매니저의 주 업무가 가장 약하게 보이던 상태를 바로잡는다.
카드 단위로 주 동작을 하나씩 두면 설정 화면처럼 카드가 여러 개인 경우에도 규칙이 일관된다.
기존 토큰과 클래스만 쓰고 새 변형을 만들지 않았다.

**제외한 대안**
- 화면당 primary 를 딱 1개로 제한: 설정 화면은 독립된 카드가 4개라 어느 하나만 강조하면
  나머지 저장 동작이 부차적으로 보인다.
- primary 를 그대로 두고 secondary 를 약화: 대비만 커지고 무엇이 주 동작인지는 여전히 모른다.

**영향 파일** `templates/projects.html`, `campaigns.html`, `project-utm-templates.html`,
`project-settings.html`, `project-members.html`

**검증** 화면별 primary 개수 확인. projects 3, campaigns 4, utm-templates 2, settings 3, members 1.

## 5. 태블릿 아이콘 레일 회귀 수정 (재수색 #3)

**문제와 맥락**
직전 반응형 작업에서 태블릿(768~1023px) 레일을 64px 아이콘 스트립으로 바꾸면서 두 가지
회귀가 생겼다. 아이콘만 남아 마우스 사용자가 뜻을 알 수 없었고, 필터·정렬 버튼을
`display: none` 으로 숨겨 콘텐츠를 걸러낼 방법이 사라졌다.

**채택안**
레일 폭을 64px → 88px 로 넓혀 필터·정렬 버튼을 세로로 배치해 되살린다.
모든 레일 항목에 `title` 을 달아 아이콘만 보이는 상태에서도 뜻을 알 수 있게 한다.
정적 항목 4개는 템플릿에, 동적 콘텐츠 항목은 `renderProjectItems()` 에서 설정한다.

**선택 근거**
88px 는 998px 기준 본문을 약 860px 확보한다. 64px 대비 24px 만 내주고 기능을 되찾는 편이,
본문 폭을 위해 기능을 없애는 것보다 낫다. `title` 은 새 컴포넌트 없이 마우스 힌트를 준다.

**제외한 대안**
- 필터·정렬을 아이콘 버튼으로 축약: 라벨이 `전체 / 캠페인만 / 단일링크만` 처럼 상태에 따라
  바뀌는 순환 버튼이라 아이콘으로 현재 상태를 표현하기 어렵다.
- 태블릿도 드로어로 전환: 프로젝트 내부 맥락을 항상 보여야 한다는 요구와 어긋난다.
- 커스텀 tooltip 컴포넌트: 네이티브 `title` 로 충분하고 새 코드가 필요 없다.

**남은 확인 사항**
아이콘만 보이는 상태에서 접근명은 `.sr-only` 방식(1×1, `clip`)으로 DOM 에 남아 있다.
브라우저 확장의 접근성 트리가 이 링크들을 이름 없음으로 보고한 적이 있어, 실제 스크린리더로
한 번 더 확인하는 편이 좋다. `title` 추가로 접근명 경로는 하나 더 확보됐다.

**영향 파일** `static/css/srrrg/projects.css`, `templates/projects.html`,
`static/js/srrrg-projects.js`

**검증**
브라우저 창 리사이즈가 세션 중간부터 뷰포트에 반영되지 않아, 같은 출처 iframe 을 실제 폭으로
띄워 측정했다. iframe 안에서는 미디어쿼리가 iframe 뷰포트 기준으로 평가되므로 실제 렌더 결과다.

| 폭 | 티어 | 레일 | 본문 | 필터·정렬 | 드로어 트리거 | 가로 오버플로 |
|---|---|---|---|---|---|---|
| 1108px | desktop | 290px | 750px | 노출 | 숨김 | 0 |
| 900px | tablet | 88px | 743px | 노출 | 숨김 | 0 |
| 400px | mobile | 300px 드로어 | 363px | 노출 | 노출 | 0 |

레일 항목 `title` 은 정적 4개와 동적 콘텐츠 항목 모두에서 확인
(`단축링크 생성`, `캠페인 생성`, `UTM 템플릿 관리`, `프로젝트 설정`, `캠페인 · 링쥐캠페인`).

## 6. 프로젝트 0개 빈 상태 (재수색 #1)

**문제와 맥락**
`loadProjects()` 는 프로젝트가 하나라도 있으면 첫 항목을 자동 선택하므로 이 패널은
0개일 때만 보인다. 그런데 문구가 `프로젝트를 선택하세요` 였고 생성 버튼이 없어,
가입 직후 사용자에게 선택할 것도 만들 방법도 없는 화면이 됐다. 유일한 출구는
제목 옆 라벨 없는 `+` 글리프였다.

**채택안**
문구를 `아직 프로젝트가 없습니다` 로 바꾸고 프로젝트가 무엇인지 한 문장으로 설명한다.
기존 `create-project-dialog` 를 그대로 여는 `첫 프로젝트 만들기` primary CTA 를 추가한다.
`+` 버튼과 `▾` 프로젝트 선택 글리프에 `title` 을 달아 마우스에서도 뜻이 드러나게 한다.

**선택 근거**
빈 상태는 "왜 비었는지 + 다음 행동" 을 줘야 한다. 새 다이얼로그를 만들지 않고 기존 것을
재사용하면 검증·포커스 처리가 이미 갖춰진 경로를 그대로 쓴다. `+` 는 이미
`aria-label` 이 있어 스크린리더는 문제없었고 마우스 힌트만 부족했다.

**제외한 대안**
- 프로젝트 0개면 다이얼로그를 자동으로 띄우기: 맥락 설명을 읽기 전에 입력을 요구하고,
  Esc 로 닫으면 다시 빈 화면이라 같은 문제로 돌아온다.
- 온보딩 단계에 프로젝트 생성 추가: `onboarding.html` 은 이름·이메일 확인 용도이며
  이번 범위를 넘어선다.
- `+` 를 텍스트 버튼으로 교체: 제목 줄 레이아웃을 다시 잡아야 하고 이번 목표를 넘어선다.

**영향 파일** `templates/projects.html`, `static/js/srrrg-projects.js`,
`static/css/srrrg/projects.css`

**검증** 빈 상태 패널을 노출시켜 CTA 클릭 시 `create-project-dialog` 가 열리고 이름 입력에
포커스가 가는 것을 확인. `+` 버튼과 동일 경로를 공유.

**참고**
당시에는 빈 상태의 `GET STARTED` 영문 kicker 를 범위 밖으로 두었다. 이후 12번에서
영문 kicker 전반을 정리하며 함께 제거했다.

## 8. 44px 미만 클릭 타깃 (재수색 #8)

**문제와 맥락**
`base.css` 가 `--control-height: clamp(44px, …)` 와 `--button-height` 를 정의해 놓고도
여러 클래스가 하드코딩으로 이탈해 있었다. 헤더 내비 링크 19px, 콘텐츠 필터 칩 25px,
기간 칩 32px, `.compact-action` 38px, `.copy-button` 34~36px, `.quick-expire-option` 38~42px,
제목 옆 글리프 버튼 36×36px.

**채택안**
독립 버튼과 컨트롤은 모두 토큰(`--button-height` / `--control-height`)으로 되돌린다.
헤더 내비 링크는 `inline-flex` + 패딩으로 44px 를 확보한다.
레일 안 필터·정렬 칩만 예외로 `min-height: 32px` 를 두고 이유를 주석에 남겼다.

**선택 근거**
제품이 스스로 정한 기준을 따르는 것이 개별 판단보다 일관된다. `.copy-button` 은 옆에 놓인
입력이 이미 `--control-height` 라 44px 로 올리면 정렬까지 함께 맞는다.

**제외한 대안**
- 전부 44px 강제: 레일 heading 안 보조 칩까지 44px 로 만들면 태블릿에서 두 개가 세로로
  쌓여 88px 을 차지하고, 목록보다 컨트롤이 무거워진다.
- 그대로 두기: WCAG 2.5.8 의 24px 는 통과하지만 자체 기준과 어긋난 채 남는다.

**트레이드오프**
레일 칩 32px 는 44px 기준에는 미달이다. 밀도를 위한 의도적 예외이며 AA 요건은 만족한다.

**영향 파일** `static/css/srrrg/components.css`, `management.css`, `projects.css`, `layout.css`

**검증** 실측 — 헤더 내비 72×45, `+` 45×45, 프로젝트 선택 45×45, 복사 64×45,
기간 칩 58×45, 적용 50×45, 레일 칩 38×40.

## 9. 통계 필터 정렬과 토큰 (재수색 #9)

**문제와 맥락**
`statistics.css` 가 한 줄로 압축된 채 `rem` 값과 `#eef3f7` 같은 hex 를 직접 써서
나머지 화면과 토큰이 어긋났다. 필터 행의 컨트롤 높이도 32/38/40px 로 제각각이었다.

**정정**
처음 보고에서 "baseline 3개로 정렬이 깨졌다" 고 했는데, 측정한 값은 각 요소의 **위쪽** 좌표였다.
`align-items: end` 로 아래쪽은 이미 정렬돼 있었고 이는 라벨 있는 필드와 없는 컨트롤이 섞인
필터 행에서 의도된 패턴이다. 실제 결함은 컨트롤 높이 불일치와 좁은 폭에서의 줄바꿈이었다.

**채택안**
파일을 토큰 기반으로 다시 쓰고 나머지 CSS 와 같은 서식(탭 인덴트, 한 속성 한 줄)을 따른다.
입력·셀렉트를 `--control-height` 로 올려 같은 행의 기간 칩·적용 버튼과 높이를 맞춘다.

**제외한 대안** 압축 형식 유지하고 값만 토큰으로 치환 — 저장소의 다른 CSS 와 계속 어긋난다.

**영향 파일** `static/css/srrrg/statistics.css`

**검증** 998px 실측 — 5개 컨트롤이 모두 아래쪽 814px 한 줄로 정렬, 줄바꿈 없음.

## 18. 링크 목록 탭의 가로 스크롤 (검증 중 발견)

**문제와 맥락**
#7~#17 검증 중 태블릿·모바일에서 링크 목록 탭이 페이지 전체를 가로로 밀어내는 것을 발견했다.
실제로 `window.scrollX` 가 모바일에서 330px, 태블릿에서 73px 까지 움직였다.
`.campaign-link-table-wrap` 에 `overflow-x: auto` 가 있는데도 문서가 밀렸다.

원인은 두 겹이었다. 래퍼가 grid 아이템이라 기본 `min-width: auto` 로 테이블의 min-content
폭까지 늘어났고, 더 결정적으로 `<th>` 안의 `.sr-only` 가 `position: absolute` 인데
위치 지정 조상이 없어 이 스크롤 컨테이너의 클리핑을 벗어나 문서를 밀어냈다.

**채택안** 래퍼에 `min-width: 0` 과 `position: relative` 를 함께 넣는다.
같은 패턴이 재발하지 않도록 통계 표의 `.data-table-wrap` 에도 적용했다.

**선택 근거**
`.sr-only` 를 지우면 표 헤더의 접근명이 사라진다. 컨테이닝 블록을 래퍼로 잡으면
접근명을 유지한 채 클리핑 안으로 들어온다. 두 가설을 각각 실험해 확인했다 —
`position: relative` 만으로도, `.sr-only` 제거만으로도 문서 스크롤이 사라졌다.
접근성을 지키는 쪽을 택했다.

**제외한 대안**
- `.sr-only` 를 `visibility: hidden` 등으로 대체: 접근명이 사라진다.
- 좁은 폭에서 표를 카드형으로 전환: 이번 범위를 넘는 구조 변경이다.

**영향 파일** `static/css/srrrg/campaigns.css`, `management.css`

**검증** 1200 / 900 / 400px, 개요·링크 목록 탭에서 `window.scrollX` 가 0 으로 유지.
표는 래퍼 안에서만 가로 스크롤되고 `.sr-only` 2개는 그대로 남아 있다.

## 19. 통계에서 여는 링크·캠페인의 목적지 (전체 진단 C-1, H-5)

**문제와 맥락**
프로젝트 개요 통계의 "캠페인 비교" 표에서 캠페인 이름이 링크인데 목적지가
`/statistics` 였다. 이 라우트는 존재하지 않는다 — `HomeController` 주석이
"단독 라우트를 두면 프로젝트 컨텍스트가 없는 화면이 렌더링되므로" 만들지 않았다고
적어 두었는데 통계 코드만 폐기된 주소를 계속 가리켰다. 로그인 화면에서 표의 링크를
그대로 fetch 해 확인한 결과 두 건 모두 HTTP 404 였다.

같은 파일의 "링크 유입 상태" 표는 `/manage?projectId=..&code=..` 로 갔다. 200 이지만
비회원 secret key 화면의 껍데기라 레일도 프로젝트 헤딩도 없다. 반면 링크 목록 탭에서
같은 링크를 열면 `/projects?..&linkCode=` 로 간다. 동일한 동작에 목적지가 둘이었다.

**채택안**
두 함수를 `workspaceUrl()` 하나로 합쳐 전부 `/projects` 뷰로 보낸다.
`from`·`to`·`bucket` 을 함께 실어 비교에서 상세로 넘어가도 기간이 끊기지 않는다.

**선택 근거**
`/statistics` 라우트를 새로 만드는 대신 이미 있는 진입점을 재사용하면 새 템플릿·CSS·라우트가
필요 없다. 레일이 쓰는 목적지가 이미 캠페인 통계를 개요 탭에 렌더하므로 화면도 그대로다.

**제외한 대안**
- `/statistics` 라우트 신설: `HomeController` 가 의도적으로 피한 "컨텍스트 없는 조각 단독 렌더" 를 되살린다.
- 링크를 그냥 제거: 비교에서 상세로 파고드는 것은 캠페인 매니저의 핵심 동선이다.

**영향 파일** `static/js/srrrg-statistics.js`

**검증** 표의 링크를 화면에서 fetch 해 404 에서 200 으로, 목적지 `/statistics` 에서 `/projects` 로 확인.
링크 유입 상태 표도 `/manage` 에서 `/projects?linkCode=` 로 바뀌어 링크 목록 탭과 일치.

## 20. 태블릿 아이콘 스트립 폐기 (전체 진단 H-1, #7 의 88px 결정 되돌림)

**문제와 맥락**
768~1023px 에서 레일이 88px 아이콘 스트립으로 줄면서 콘텐츠 목록의 라벨을
1x1 크기와 `clip: rect(0,0,0,0)` 으로 잘랐다. 캠페인이 N개면 같은 28x28 "C" 글리프가
N개 쌓인다. 실측으로 항목 2개에 구분되는 글리프 1개였다.

#7 에서 이 구간에 `title` 을 달아 "마우스에서도 뜻이 드러나게" 했지만,
이 브레이크포인트의 주 대상인 터치 태블릿에서는 `title` 이 뜨지 않는다.
완화책이 대상 기기에서 작동하지 않으니 트레이드오프가 성립하지 않았다.

**채택안**
아이콘 스트립 블록을 삭제하고 드로어 경계를 767px 에서 1023px 로 올려 2단으로 만든다.

**선택 근거**
드로어는 이미 라벨·포커스 이동·복귀·Escape·스크림을 갖췄다. 새 컴포넌트가 필요 없고
반응형 단계가 셋에서 둘로 줄어 규칙이 순감했다. 드로어 안에서 라벨을 되살리던 규칙도
clip 하는 쪽이 사라져 함께 지웠다.

**제외한 대안**
- 스트립을 220px 로 넓혀 목록만 라벨 노출: 규칙이 늘고 본문 폭이 132px 줄어든다.
  태블릿 상시 내비게이션이 제품 요구사항이 되면 그때 택할 수 있다.
- `title` 대신 `aria-label` 추가: 보는 사람에게는 여전히 같은 글리프다.

**영향 파일** `static/css/srrrg/projects.css`, `src/test/.../ProjectsPageAssetTest.java`

**검증** 실제 배포된 `@media(max-width:1023px)` 규칙을 CSSOM 에서 꺼내 강제 적용해 측정.
라벨 clip true 에서 false 로, 구분되는 텍스트 1 에서 2 로(항목 2개), 레일이 드로어로 전환됨.

## 21. 캠페인 링크 표를 카드형으로 접기 (전체 진단 H-2, #18 에서 제외했던 대안 채택)

**문제와 맥락**
진단 초기에 이 문제를 모바일 한정으로 봤는데 실측 결과 1064px 노트북에서 이미 잘렸다.
레일 290px 을 뺀 본문에서 래퍼는 648px 인데 `.campaign-link-table` 에
`min-width: 900px` 이 걸려 있어 뒤쪽 세 열(생성일·UTM·복사)이 항상 시야 밖이었다.
가장 많이 쓰는 복사 버튼과 UTM 확인 배지가 둘 다 기본 상태에서 보이지 않았다.

모바일에서는 같은 페이지의 `.activity-table` 은 카드로 접히는데
`.campaign-link-table` 만 760px 가로 스크롤러로 남았다. 그런데
`srrrg-campaigns.js` 의 `tableCell()` 은 이미 모든 셀에 `data-label` 을 넣고 있었다 —
카드형에 필요한 훅이 다 깔린 채 CSS 만 붙지 않은 상태였다.

#18 에서 "좁은 폭에서 표를 카드형으로 전환" 을 범위를 넘는다는 이유로 제외했는데,
데스크톱 잘림까지 확인되면서 그 판단을 뒤집었다.

**채택안**
- 카드형 규칙을 `components.css` 의 `.stacking-table` 로 추출하고 `management.css` 의 중복 블록 삭제.
- `.activity-table` 과 `.campaign-link-table` 이 같은 클래스를 공유.
- 표 `min-width` 를 900px 에서 640px 로 낮춤.
- 복사·UTM 을 단축 코드 옆으로 옮기고 표 안 생성일을 축약형으로(전체 시각은 `title`).

**선택 근거**
규칙을 복사하면 같은 블록이 두 파일에 생긴다. 공용 클래스로 올리면 순감이고
`data-label` 이 이미 있어 JS 변경이 0줄이다. 열을 지우지 않고 순서와 형식만 바꿔
정보량을 유지한 채 주 동작을 시야로 끌어왔다.

**제외한 대안**
- 열 삭제(external_id 등): 링크 검수에 쓰이는 정보다.
- 목적지 `max-width` 를 200px 로 더 줄이기: 긴 URL 이 있을 때의 가로 스크롤을 없애려고
  모든 경우의 가독성을 희생한다. 340px 유지 후 필요할 때만 스크롤이 낫다.
- 축약 날짜를 `title` 만으로 보완: #7 에서 실패한 툴팁 의존을 반복하게 된다.
  카드형에서는 `data-label` 과 함께 값이 그대로 보이고, 정확한 시각은 링크 상세에 있다.

**영향 파일** `static/css/srrrg/components.css`, `campaigns.css`, `management.css`,
`templates/campaigns.html`, `statistics.html`, `management.html`,
`static/js/srrrg-campaigns.js`, `srrrg-statistics.js`, `src/test/.../CampaignsPageAssetTest.java`

**검증** 1064px 에서 잘린 열 3개에서 0개로, 표 필요폭 900px 에서 645px 로(래퍼 648px), 가로 스크롤 없음.
모바일 규칙 강제 시 `thead: none`, `td: grid`, `::before` 가 "이름"·"우리 쪽 식별자" 로 렌더.

## 24. 예외 화면의 헤더 계정 상태 (전체 진단 H-4, b0588dc 의 잔여 인스턴스)

**문제와 맥락**
세션이 유효한데도 링크 오류 화면만 헤더가 로그아웃(로그인 버튼)으로 렌더됐다.
같은 순간 `/projects` 는 계정 메뉴를 렌더한다. 원인은 `WebAccountModel` 이
`@ControllerAdvice` 의 `@ModelAttribute` 인데 `@ExceptionHandler` 가 렌더하는 뷰에는
이 어드바이스가 적용되지 않는다는 Spring 동작이다.

`WebAccountModel` 의 javadoc 이 이 버그 계열을 이미 문서화하고 만료 토큰 폴백까지
구현해 뒀지만, 예외 핸들러 경로는 어드바이스가 실행조차 되지 않아 그 수정이 닿지 못했다.
링크 오류 화면은 앱 외부에서 진입하는 유일한 화면이라 노출 빈도가 높다.

**채택안**
표시용 계정 조회를 `WebAccountModel.apply(request, model)` 로 분리하고
`RedirectExceptionHandler.errorPage()` 에서 호출한다. 핸들러 네 개가 한 번에 커버된다.
principal 은 `SecurityContextHolder` 에서 읽어 네 개 메서드 시그니처를 건드리지 않는다.

**선택 근거**
`errorPage()` 한 곳만 고치면 404·410·403·503 전부 해결된다. 만료 토큰 폴백과
"권한은 부여하지 않고 표시용으로만 읽는다" 는 기존 설계 의도가 그대로 유지된다.

**제외한 대안**
- 각 핸들러에 `@AuthenticationPrincipal` 인자 추가: 네 곳에 같은 변경이 반복된다.
- `HandlerInterceptor.postHandle` 로 옮기기: 예외가 발생하면 `postHandle` 이 호출되지 않는다.

**영향 파일** `auth/WebAccountModel.java`, `link/redirect/RedirectExceptionHandler.java`,
`src/test/.../RedirectControllerTest.java`

**검증** 동일 세션·동일 시점에 없는 코드와 `/projects` 의 헤더를 비교해 mismatch 가 사라짐.
쿠키 없는 요청에서는 계속 로그인 버튼이 나오는 것도 확인.
오류 화면이 계정 정보를 채우는지 검증하는 테스트를 추가했다.

## 25. 중복 API 호출과 통계 조각의 토큰 갱신 (전체 진단 H-6 1단계)

**문제와 맥락**
캠페인 하나를 여는 데 API 11건이 나가고 그중 3건이 완전 중복이었다.
`srrrg-projects.js`·`srrrg-campaigns.js`·`srrrg-statistics.js` 가 한 페이지에서
각각 독립 초기화되며 서로를 모른다. 특히 가장 비싼 통계 쿼리가 두 번 실행됐다.

검증 중에 더 큰 문제를 발견했다. `srrrg-statistics.js` 만 맨 `fetch` 를 써서
401 에서 refresh 재시도에 참여하지 못했다. access token 이 만료된 채 화면에 들어오면
나머지는 전부 갱신으로 살아나는데 통계만 "로그인이 필요합니다" 로 남았다.
그 안내 문구 자체가 이 결함의 우회였다.

**채택안**
- 통계 조각은 캠페인 뷰에서 초기 `load()` 를 건너뛴다(`campaigns.js` 가 컨텍스트 확정 후 호출).
- 템플릿 목록은 "새 캠페인" 폼이 없는 뷰에서 부르지 않는다.
- URL 에 `projectId` 가 있으면 프로젝트 개요의 통계 재조회를 생략한다.
- 서브도메인은 `SrrrgCommon.requestShared()` 로 응답을 공유한다.
- 통계 조각을 `SrrrgCommon.request` 로 옮겨 갱신 흐름에 넣는다.

**선택 근거**
호출 조건을 좁히는 일이라 내비게이션 방식을 바꾸지 않는다.
`requestShared` 는 호출한 쪽이 "이 페이지에서 안 바뀐다" 고 판단한 URL 만 명시적으로
넘기는 옵트인이라, 변경 후 재조회가 있는 다른 엔드포인트에는 영향이 없다.

**제외한 대안**
- 진행 중 GET 을 자동으로 합치는 계층: 실제로 넣어 보고 측정했더니 명시적 가드가
  이미 일을 다 해서 아무것도 잡지 못했다. 두 subdomain 요청은 시간상 겹치지 않아
  합칠 수도 없었다. 6줄을 도입해 0건을 막는 계층이라 삭제했다.
- 만료 시간을 둔 GET 캐시: 변경 직후 재조회가 stale 을 읽을 위험을 60ms 요청 하나와 바꾼다.

**영향 파일** `static/js/srrrg-common.js`, `srrrg-projects.js`, `srrrg-campaigns.js`, `srrrg-statistics.js`

**검증** 캠페인 화면 중복 3건에서 0건으로, 프로젝트 개요 0건.
통계가 만료 토큰 상태에서도 갱신 후 정상 렌더.

## 26. 프로젝트 개요의 정보 위계 (전체 진단 M-1)

**문제와 맥락**
"프로젝트 개요" 카드 하나에 링크·캠페인 수, 도메인, 통계 리포트 전체, 멤버 관리가
모두 들어 있었다. 실측으로 카드 2035px 중 통계가 1717px(84%)이고,
`h2 개요` 아래 `h3 통계` 아래 `h4` 5개로 위계가 뒤집혔다. 카드 제목이 "개요" 인데
내용의 대부분이 분석 리포트라 라벨과 내용이 어긋났다.

**채택안**
- 링크·캠페인 수와 도메인은 "프로젝트 요약" 카드로 남기고 항상 보이게 둔다.
- 통계와 멤버를 캠페인 상세와 같은 `console-tabs` 로 나눈다. 기본 탭은 통계다.
- 조각들이 이미 자기 `surface-panel` 을 들고 오므로 탭 패널에 카드 클래스를 겹치지 않는다.

**선택 근거**
워크스페이스에 들어오면 먼저 데이터가 보여야 한다는 톤 원칙 때문에 통계를 기본 탭으로 뒀다.
수·도메인은 작고 자주 쓰는 값이라 탭 뒤로 숨기지 않았다. `console-tabs` 는 이미 있는
컴포넌트라 새 CSS 가 0이고, 캠페인 상세와 같은 조작 방식이 되어 화면 간 일관성이 생긴다.

**제외한 대안**
- 통계를 형제 섹션으로만 분리: 위계는 고쳐지지만 기본 스크롤 길이가 그대로다.
- 개요를 기본 탭으로: 진입 직후 화면이 수치 두 개만 남아 "바로 데이터가 보여야 함" 에 어긋난다.
- 통계 표 3개를 `details` 로 접기: 분석 본문을 접는 셈이라 이 화면의 목적을 해친다.

**한계** 기본 스크롤은 2740px 에서 2664px 로 76px 만 줄었다. 통계 리포트 자체의 길이가
지배적이고 그게 기본 탭이기 때문이다. 이 항목의 실질은 스크롤 단축이 아니라
위계·라벨 정합성과 멤버 관리의 분리다.

**영향 파일** `templates/projects.html`, `static/js/srrrg-projects.js`

**검증** 위계가 `H1 내 프로젝트`, `H2 프로젝트 요약`, `H3 통계` 로 정리됨.
탭 roving tabindex 동작(좌우 방향키로 전환, Tab 순서에는 선택된 탭만), 콘솔 오류 0.

## 27. 랜드마크·제목 중첩 (전체 진단 M-7)

**문제와 맥락**
`management.html` 의 `th:fragment="workspace"` 가 `<main>` 을 감싸고 있어서
`projects.html` 의 링크 상세 뷰에서 `<main>` 안에 `<main>` 이 들어가고
보이는 `<h1>` 이 두 개가 됐다.

**채택안**
조각 경계를 `<main>` 안쪽으로 옮기고, 단독 페이지의 `<main>` 에는
`<h1 class="sr-only">` 를 둔다. 조각 안의 제목 두 개는 `h2` 로 낮췄다.

**선택 근거**
조각이 페이지 껍데기를 들고 가지 않는다는 이 저장소의 기존 원칙과 같은 방향이다.
단독 페이지에서는 게이트 제목이 화면에 보이고 sr-only h1 이 문서 제목을 담당해
두 맥락 모두 h1 이 정확히 하나가 된다.

**제외한 대안**
- 조각 안 제목을 그대로 h1 으로 두기: 삽입되는 쪽에 h1 이 둘 남는다.
- 단독 페이지에 보이는 h1 추가: 게이트 제목과 같은 문장이 두 번 나온다.

**주의** `management.css` 가 이 제목들을 `h1` 선택자로 잡고 있어 함께 `h2` 로 바꿨다.
바꾸지 않으면 주 제목이 기본 h2 크기로 작아진다.

**영향 파일** `templates/management.html`, `static/css/srrrg/management.css`

**검증** 링크 상세 뷰에서 `<main>` 이 2개에서 1개로, 중첩 없음, 보이는 h1 1개,
제목 글자 크기 31.9px 유지. `/manage` 단독 페이지도 main 1개와 h1 1개.

## 28. 남은 Medium·Low 일괄 정리

**M-3 UTM 표준 필드 유도** 필드 이름이 자유 입력뿐이라 실제 프로젝트가
`utm1`·`utm2`·`utm3` 으로 만들어져 있었고, 그 이름이 통계의 UTM별 집계 키로 그대로 올라갔다.
`<datalist>` 로 표준 5개(`utm_source`/`utm_medium`/`utm_campaign`/`utm_term`/`utm_content`)를 제시한다.
자유 입력을 막지 않는 쪽을 골랐다 — 내부 규칙이 있는 팀도 있고, `pattern` 이 이미 형식을 지킨다.
`<select>` 로 강제하는 대안은 표준 밖 필드를 아예 못 만들게 해 제외했다.

**M-4 최종 URL 미리보기** UTM 값을 채워도 결과 주소를 볼 수 없었다.
목적지와 유효 UTM(입력값 우선, 없으면 캠페인 기본값)을 조립해 폼 아래에 보여준다.
서버 계산과 같은 규칙이고 값이 이미 클라이언트에 있어 왕복이 없다.
목적지가 없으면 "이동하지 않습니다" 를 같은 자리에서 알린다.

**M-5 요청 식별자** `readonly` 로 UUID 를 폼 한 줄에 보여줬다. 사용자가 읽거나 고칠 값이
아니라 `type="hidden"` 으로 옮기고 "중복 생성되지 않습니다" 설명만 남겼다.
JS 의 자동 발급 로직은 그대로다.

**M-6 external_id 용어** 라벨이 금지 안내를 겸하고 있었다.
라벨은 "우리 쪽 식별자 (선택)" 로, 금지 사항과 예시는 `.help-text` 로 분리했다.
표 헤더와 카드 라벨, 내보내기 검색 라벨도 같이 맞췄다.
API 와 CSV 양식 헤더는 계약이므로 `external_id` 를 그대로 둔다 — 도움말에 그 사실을 적었다.
이전 커밋에서 표 헤더만 먼저 바꿨다가 통계 표·CSV 와 어긋나 되돌린 적이 있어 이번에 한 번에 처리했다.

**M-9 비활성 컨트롤의 이유** 서브도메인 선점 전에는 "활성화" 체크박스와 "반납" 이
`disabled` 인데 이유가 없었다. 상태에 따라 문구가 바뀌는 `#subdomain-availability` 를 두고
두 컨트롤에 `aria-describedby` 로 연결했다. 선점 후에는 현재 값을 보여준다.

**M-10 드로어 포커스 트랩** 스크림으로 덮인 상태에서 외부 포커스 가능 요소 22개가
Tab 으로 도달됐다. 덮이는 영역에 네이티브 `inert` 를 준다.
레일이 `<main>` 안에 있어 body 자식만 걸러면 본문이 남으므로 영역을 직접 지정했다.
직접 만든 focus trap 대신 `inert` 를 쓴 이유는 포인터까지 함께 막히고,
비회원 결과 패널에서 이미 쓰는 방식이라 관례가 일치하기 때문이다.

**M-11 편집자의 설정 접근** 레일의 설정 항목이 소유자 전용인데 설정 화면에는
편집자용 "기존 익명 링크 편입" 이 있어 직접 URL 말고는 도달할 수 없었다.
진입 조건을 `canEdit` 으로 넓히고, 소유자 전용 카드는 그대로 숨긴 채
편집자에게 왜 나머지가 안 보이는지 알리는 문구를 추가했다.
편입을 소유자 전용으로 좁히는 대안도 있었지만, 링크 편집 권한자가 자기 링크를
프로젝트로 옮기는 것은 편집 행위의 범위라고 판단했다.

**M-12 기간 칩 선택 상태** `aria-pressed` 가 없어 어느 기간이 선택됐는지 알 수 없었다
(같은 컨트롤이 `management.html` 에는 있다). 칩에 `aria-pressed` 를 넣고
`setPeriod()` 에서 갱신한다. URL 파라미터로 들어온 기간이 7·30·90일과 정확히 맞으면
그 칩을 선택으로 표시하고, 날짜를 직접 고치면 표시를 지운다.

**M-13 통계 필터의 폼 컴포넌트** 맨 `<label>` 을 써서 제품 공통 폼에서 이탈해 있었다.
`.field`/`.field-label`/`.field-input` 으로 교체하고, 높이·배경·테두리를 개별 보정하던
`statistics.css` 규칙을 삭제했다(순감).

**M-14 터치 타깃** `.text-button` 이 `padding: 4px` 만 두어 UTM 필드 삭제가 22px,
서브도메인 반납이 25px 로 렌더됐다 — 파괴적 동작인데 제품이 스스로 정한 44px 기준에
미달이었다. 글자 크기는 그대로 두고 `min-height: var(--button-height)` 로 클릭 영역만 넓혔다.
남은 32~38px 컨트롤(레일 필터·정렬, 계정 메뉴, 프로젝트 선택)은 그대로 둔다 —
모두 WCAG 2.5.8 AA 의 24px 를 넘고, 레일 칩 32px 은 #7 에서 밀도를 이유로
의도적으로 고른 예외라고 주석에 기록돼 있다.

**M-15 헤더의 "링크 관리"** 로그인 사용자에게도 비회원 secret key 게이트를 노출해
두 제품 층위가 헤더에서 섞였다. `accountUser == null` 일 때만 보이게 했다.
기존 익명 링크를 옮기는 경로는 프로젝트 설정의 편입 기능이 담당한다.

**L-1 오류 화면 문구 중복** 제목과 설명이 같은 문장이었다.
예외 메시지는 로그·API 용으로 두고, 화면 설명에는 원인과 다음 행동을 담았다.

**L-3 계정 아바타** 모두에게 "내" 를 보여줬다. 표시 이름의 첫 글자를 쓴다.

**L-4 들여쓰기** `#campaign-link-empty` 블록의 어긋난 들여쓰기를 정리했다.

**L-5 죽은 마크업** `#campaign-picker-panel` 이 `hidden` 으로 유지됐다.
JS 가 실제로 쓰는 것은 `<select>` 하나뿐이라 패널과 `h3`, `label` 을 지웠다.

`static/js/srrrg-campaigns.js`, `srrrg-statistics.js`, `srrrg-projects.js`, `srrrg-project-settings.js`,

## 29. 이번 범위에서 고치지 않은 항목과 이유

**H-6 2단계 — 패널 전환을 클라이언트 렌더로 바꾸기**
레일 클릭·캠페인 열기·링크 열기가 모두 전체 페이지 이동이다. 이를 `fetch` 와
`history.pushState` 로 바꾸면 `projects.html` 의 Thymeleaf `th:if` 분기를 클라이언트로
옮기는 작업이 되어, 이 저장소가 공들여 온 포커스 관리와 라이브 리전 배치를 전부
재검증해야 한다. 스크린샷을 얻을 수 없는 상태(창이 표시되지 않아 렌더러가 프레임을
합성하지 않음)에서 그 규모의 구조 변경을 시각 검증 없이 넣는 것은 위험이 이득을 넘는다.

대신 키보드 사용자가 실제로 겪던 손실만 없앴다. 이동 후 포커스가 `body` 로
떨어지던 것을, 열린 패널의 제목(이미 `tabindex="-1"` 이 있는 요소)으로 옮긴다.
"레일에서 왔는지" 를 저장하지 않고 URL 파라미터로 판단한다 — 이 화면의 상태는 전부
쿼리파라미터에 있고, `ProjectsPageAssetTest` 가 `sessionStorage` 사용을 금지한다.
처음에 `sessionStorage` 로 구현했다가 그 테스트에 걸려 URL 판단으로 바꿨고,
결과적으로 직접 링크와 새로고침에서도 동작하는 더 나은 방식이 됐다.

**M-16 브레이크포인트 수렴 (부분만 적용)**
380·520·560·640·700·720·767·900·980·1023px 이 6개 파일에 흩어져 있다.
이번에는 같은 화면의 같은 의도가 20px 차이로 갈라진 곳 하나만 맞췄다 —
통계 필터 700px 을 720px 로(같은 화면의 표가 720px 에서 접힌다).
`management.css` 의 640·900px 은 밀도 높은 분석 레이아웃 전체를 지배하고,
`account.css` 720px 과 `invitation.css` 560px 은 각자 독립 화면이다.
시각 확인이 불가능한 상태에서 이들을 옮기면 내가 볼 수 없는 회귀가 남는다.
수렴 자체는 유지보수 항목이라 시각 검증이 가능한 시점에 별도로 진행하는 것이 맞다.

**L-2 `@import` 체인 (미적용)**
`srrrg.css` 가 10개를 `@import` 하고 `projects.html` 은 추가로 2개를 직접 로드한다.
`@import` 는 부모 CSS 를 파싱한 뒤에야 발견되므로 직렬 지연이 생긴다.
다만 실제 비용은 파일 10개가 아니라 발견 왕복 1회다(발견 후 10개는 병렬 요청).
이를 없애려면 8개 템플릿의 `<head>` 마다 `<link>` 10줄을 복제해야 하고,
그 순서가 곧 캐스케이드라 한 곳만 틀려도 조용히 스타일이 깨진다.
번들 단계가 없는 지금 구조에서는 유지 비용과 실수 위험이 왕복 1회보다 크다고 판단했다.
CSS 번들링을 도입하는 시점에 함께 처리할 항목이다.

**M-2 빈 상태 노출 구간 (부분)**
`campaign-link-empty` 에 `hidden` 기본값을 주어 링크가 있는 캠페인에서 잘못된 빈 상태가
